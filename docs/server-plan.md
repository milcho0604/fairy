# 페어리 서버 기획서

- 판: 5 (2026-10-14). 공지 창과 서버에서 정하는 강제 업데이트(23절)를 더했다. 4판은 법률 검토(22절)를 반영해 서버 기능에 나이 확인을 두고, 만 14세 미만은 앱 안 모드, AI 대화권은 만 18세 이상으로 바꿨다.
- 상태: 기획 확정, 개발 전. 관련 이슈 #79.
- 이 문서가 정하는 것: 서버가 맡을 일과 사용자 앱이 맡을 일의 경계, 계정, 코인, AI 대화권, 이벤트, 공지와 강제 업데이트, 백업, 운영.

## 1. 목적
- 친구들이 쓰는 지금 규모에서 운영자가 코인과 이벤트를 직접 관리한다.
- 운영자의 Claude Max 월 API 크레딧으로 사용자에게 AI 대화권을 준다.
- 기기를 바꿔도 코인, 산 물건, 캐릭터, 할 일을 되찾을 수 있게 한다.
- 서버 부담과 운영 비용은 최소로, 서버가 꺼져도 앱은 거의 그대로 쓰게 한다.

### 하지 않는 것
- 할 일, 일정, 대화 내용을 서버에 늘 맞춰 두는 동기화(백업만 한다).
- 결제, 유료 판매. 코인은 돈으로 사지 않는다.
- 이메일, 전화번호 수집. 광고, 마케팅.

## 2. 원칙
1. **사용자 앱이 기본.** 펫, 할 일, 일정, 집중, 상점, 내 컴퓨터 AI 대화는 앱 안에서 돈다.
2. **서버는 세 가지만:** 비밀을 쥐어야 하는 일(API 키), 여러 사람 사이에서 한 번만이어야 하는 일(코인 정본, 쿠폰, 지급), 사람을 알아봐야 하는 일(계정).
3. **서버가 꺼져도 앱은 멈추지 않는다.** 서버 기능만 "잠시 뒤 다시"가 되고, 밀린 일은 살아나면 맞춘다.
4. **개인정보는 최소로.** 사람은 로그인 서비스의 계정 고유 번호로만 알아본다. 만 14세 미만은 서버로 아무것도 보내지 않는다.
5. **운영 틀은 하나로.** 이미 도는 moilga daypoll 서버와 같은 방식으로 같은 맥미니에 올린다.

## 5. 계정
### 나이 확인과 두 모드 (4판)
- 앱은 처음 켤 때 서버에 아무것도 보내지 않는다. 서버 기능(기기 계정, 서버 코인, 로그인, 쿠폰, 이벤트 선물, 서버 백업, AI 대화권)을 처음 쓰려 할 때 **나이를 한 번 묻는다**: "만 14세 미만", "만 14세 이상 18세 미만", "만 18세 이상".
- **앱 안 모드(만 14세 미만, 또는 서버 기능을 켜지 않은 사람):** 지금 앱과 같다. 펫, 할 일, 일정, 집중, 코인 벌기와 쓰기, 상점, 개인 백업 파일, 내 컴퓨터 AI 를 모두 쓴다. 코인은 앱 장부(`coin_log`)에 있고 서버에는 아무것도 가지 않는다. 이벤트 목록(정적 파일)은 읽어서 보여 주되 받기는 서버 모드에서만.
- **서버 모드(만 14세 이상):** 아래 기기 계정부터 시작한다. AI 대화권은 만 18세 이상만.
- 나이 답은 앱에 둔다. 서버에는 "14세 이상" 또는 "18세 이상" 구분만 보낸다(생년월일은 받지 않는다).
- 나중에 서버 모드로 바꾸면(나이가 차거나, 보호자 동의 절차가 생기면) 앱 장부의 잔액과 산 물건을 한 번 서버로 옮긴다(6절 기존 사용자 옮기기와 같다).
- 나이를 잘못 답했다며 바꾸는 것은 설정에서. 만 14세 미만으로 바꾸면 서버 모드를 끄고 서버 계정 삭제를 안내한다.
- 보호자 동의 절차(시행령 제17조의2 의 전자우편 회신 방법 등)는 나중 선택. 생기면 만 14세 미만도 서버 모드를 쓸 수 있다.

### 기기 계정과 로그인
- 서버 모드를 켜면 서버가 **이름 없는 기기 계정**을 만들고 기기 토큰을 준다. 로그인하지 않아도 코인은 이 계정에 쌓인다.
- 로그인은 기기 계정에 구글이나 카카오를 이어 붙이는 것이다.
- 로그인이 필요한 것: 기기 옮기기(코인, 물건, 대화권 되찾기), AI 대화권, 쿠폰, 서버 백업.
- 로그인 없이 다시 설치하거나 기기를 바꾸면 기기 계정은 되찾을 수 없다. 앱에 이 점을 알린다.

### 로그인 방식
- **구글 먼저, 카카오는 나중.**
- 구글: `openid` 만 쓴다(표시 이름을 받지 않으므로 `profile` 도 뺀다). 민감 범위가 아니라 심사가 없고 사업자도 필요 없다. 일정 연동용 OAuth 앱(검수 중)과 따로 만든다.
- 카카오: 닉네임 같은 기본 항목은 사업자 없이 된다. 이메일은 받지 않으므로 비즈 앱 전환이 필요 없다.
- **이메일은 받지 않는다.** 사람은 각 서비스의 계정 고유 번호(sub)로 알아본다.
- 흐름(구글, 카카오 같음):
  1. 앱이 `127.0.0.1` 의 빈 포트에 잠깐 받는 곳을 열고(구글 캘린더 연결 `src/main/gcal-auth.ts` 와 같은 방식) 시스템 브라우저로 서버의 `/auth/<서비스>/start?port=<포트>&state=<임의값>` 을 연다.
  2. 서버가 구글이나 카카오 로그인으로 보낸다. 돌아오는 주소는 서버의 고정 주소 `https://fairy-api.moilga.com/auth/<서비스>/callback` 이다.
  3. 서버가 code 를 토큰으로 바꾸고(클라이언트 비밀은 서버에만) 계정 고유 번호를 확인한 뒤, 브라우저를 `http://127.0.0.1:<포트>/done?code=<일회용 코드>&state=...` 로 보낸다.
  4. 앱이 일회용 코드(1분, 한 번)를 `POST /v1/session` 으로 세션과 바꾼다. 세션 토큰은 safeStorage 에 둔다.
- 앱 주소(`fairy://`)로 돌아오지 않는 까닭: 사용자가 설정에서 앱 주소 받기를 끌 수 있고(`settings.urlScheme`), 루프백이 이미 검증된 방식이다.
- 카카오 확인(공식 문서): 리디렉트 URI 는 최대 10개, HTTP 와 HTTPS 만, 요청 값과 완전히 같아야 한다(다르면 KOE006). 클라이언트 시크릿은 REST API 키에 기본으로 켜져 있어 토큰 요청에 필요하다. → 서버 고정 HTTPS 콜백 하나를 등록하고 시크릿은 서버에만 두면 맞다. 회원번호(id)는 동의 항목 없이 받는 기본 정보로 보인다(구현 때 실제 응답으로 확인).

### 다른 PC 에서
| 경우 | 결과 |
|---|---|
| 새 PC 에서 같은 계정으로 로그인 | 코인, 산 물건, 대화권이 따라온다. 캐릭터와 할 일은 백업으로 |
| 로그인 없이 두 PC 에서 씀 | 기기 계정이 둘, 코인이 따로 쌓인다. 둘 다 같은 계정으로 로그인하면 한 번 합친다 |
| 이미 계정이 있는데 새 기기 계정으로 로그인 | 새 기기 계정의 코인과 물건을 계정에 더하고 기기 계정은 닫는다 |
| 한 PC 는 구글, 다른 PC 는 카카오 | 이메일로 맞출 수 없어 계정이 둘. 설정의 "카카오도 연결"로 한 계정에 둘 다 붙인다 |

### 탈퇴
- 앱 설정에서 바로. 서버의 계정, 코인 내역, 대화권, 서버 백업을 지운다. 앱 안 데이터는 남는다.

## 6. 코인
### 규칙
- 버는 값은 지금 앱 규칙 그대로다(출석 10, 7일 연속 +50, 매주 선물 50, 할 일 15, 집중 15분 5 / 25분 10 / 50분 25, 하루 상한들). 규칙 코드는 앱과 서버가 같은 파일(`src/shared/`)을 쓴다.
- 서버는 받은 기록을 같은 규칙으로 다시 확인한다. 하루 상한을 넘는 기록은 상한까지만 반영한다.

### 서버가 꺼져 있을 때와 맞추기
- 앱은 서버 잔액의 사본과 아직 안 보낸 기록(대기열)을 갖는다.
- 기록마다 앱이 만든 고유 번호가 있어, 같은 기록을 두 번 보내도 한 번만 반영된다.
- 몇 분에 한 번, 그리고 앱을 켤 때 대기열을 묶어 보낸다. 서버는 반영 결과와 새 잔액을 돌려준다.
- 쓰기는 사본 잔액 안에서만 허용한다. 서버에서 잔액이 모자라면(다른 기기에서 먼저 썼을 때) 그 구매는 서버가 거절하고 앱은 코인을 돌려주며 물건을 되돌린다.

### 기존 사용자 옮기기
- 첫 연결 때 앱의 지금 잔액과 산 물건을 한 번 서버로 올린다. 이후 정본은 서버.
- 한 기기 계정당 한 번만 받는다.

## 7. 백업
### 개인 백업 파일
- 지금 있는 백업(설정 > 데이터, 폴더로 저장)을 **파일 하나**로 바꾼다. 예: `페어리 백업 2026-10-14.fairybackup` (zip). 1.5 단계에서 만들었다(이슈 #90).
- 파일 안 맨 위의 머리 파일 `fairy-backup.json` 에 판(지금 1), 앱 판, 만든 때, 항목마다 경로와 크기와 sha256 을 적는다. 읽을 때는 항목 수(5000), 풀린 크기 합(1GB), 경로(맨 위는 아는 파일만, 그 밖은 `pets/` 아래만, `..` 와 절대 경로 금지), 머리 파일 판, crc32 와 sha256 이 하나라도 어긋나면 거절한다. 더 새 판이면 앱을 업데이트하라고 알린다.
- 복원은 OS 창 없이 설정 창 안 확인 칸에서 묻는다. 바꾸기 전 지금 데이터를 `before-import-<시각>` 에 두고, 같은 칸의 "되돌리기"로 돌아갈 수 있다.
- 들어가는 것: `jjakkung.db`(할 일, 일정, 메모, 펫 상태, 산 물건), `pets/`(캐릭터 그림), 설정과 성장, 쪽지 같은 작은 json. 지금 백업과 같은 목록이다.
- 빼는 것: 받은 모델, 그리기 모델, 로그인 셸 정보, 토큰. 지금과 같다.
- 새 PC 에서 파일을 두 번 누르거나 설정에서 가져오면 복원된다. 복원 전 지금 데이터는 따로 둔다(지금 동작과 같음).
- **코인은 백업에서 복원하지 않는다.** 서버 정본을 따른다. 옛 백업으로 코인을 늘릴 수 없다. 이 규칙은 서버 모드(로그인해 서버가 코인 정본일 때) 기준이다.
- 1.5 단계(서버 없음, 이슈 #90)에서는 코인 잔액과 내역, 산 물건의 정본이 앱의 `jjakkung.db` 라 백업에 든 앱 안 값을 그대로 복원한다. 복원 확인 칸에 "코인과 산 물건도 백업 때 것으로 바뀐다"고 적는다. 2단계에서 서버 모드가 생기면 서버 모드 사용자는 복원 뒤 서버 정본으로 다시 맞춘다(6절).
- 서버 없이 되므로 서버 단계보다 먼저 해도 된다.

### 서버 백업
- 평소에는 하지 않는다. 사용자가 **"서버에 백업"을 누를 때만** 올린다.
- 서버 모드(만 14세 이상)에서 로그인한 사람만. 계정별 **최근 2개**만 보관하고, 파일 하나 최대 20MB.
- 처음 올릴 때 "할 일, 메모, 일정에 건강이나 가족 이야기 같은 민감한 내용이 들어 있을 수 있다"를 알리고 따로 동의를 받는다(제23조). 동의하지 않으면 개인 백업 파일만 쓴다.
- 오래 쓰지 않은 계정의 서버 백업은 1년 뒤 지운다(지우기 30일 전 앱에 알림).
- 새 PC 에서 같은 계정으로 로그인하면 "서버 백업 가져오기"가 보인다.
- 서버 백업에는 할 일, 메모 같은 개인 내용이 들어간다. 서버는 디스크에 암호화해 저장하고, 탈퇴하면 바로 지운다. 개인정보처리방침에 적는다.
- 나중 선택: 사용자가 정한 비밀번호로 앱에서 잠가 올리기(서버도 못 읽음, 비밀번호를 잊으면 복구 불가).
- 크기 감: 운영자 데이터 기준 DB 약 128KB, 캐릭터 그림 약 1MB.
- 구현(#102): `PUT /v1/backup?consent=yes`(세션만, octet-stream, 20MB, 흘려 받아 AES-256-GCM 으로 볼륨 `fairy_backups` 에), `GET /v1/backup`(목록, 30일 전 `soon`), `GET /v1/backup/:id`, `DELETE /v1/backup/:id`. 키 `BACKUP_ENC_KEY` 가 비면 503 `backup_off`. "1년 미사용"은 마지막으로 올리거나 받은 때로 센다(목록 보기는 치지 않는다). 쪽지함 알림은 #101 뒤에 잇는다.
- 카카오 로그인(#102)은 기능 키 `kakao_login`(off, allowlist, everyone. 기본 off)을 따른다. allowlist 면 이미 로그인한 허용 계정이 앱에서 "카카오도 연결"하는 것만 된다(`POST /v1/auth/kakao/begin`, 세션). 앱은 `GET /v1/auth/providers` 가 알려 준 단추만 보인다.

## 8. AI 대화권
### 확인한 사실
- Max 5x 는 매달 API 크레딧 100달러, Max 20x 는 200달러. Claude API 에 쓰고 Claude Code 에는 안 쓰인다. 결제 주기마다 새로 들어오고 남은 것은 이월되지 않는다.
- 크레딧은 연결한 콘솔 조직에 들어온다. 공식 문서 표현으로 "자기 앱과 에이전트를 만들고 돌리는 데" 쓴다. 크레딧 약관은 크레딧을 남에게 넘기거나 팔지 못하고 계정 주인만 쓴다고 정한다.
- 해석: 우리 서버가 우리 키로 API 를 부르고 사용자는 답만 받으므로 넘기기가 아니라 우리 앱의 사용이다(운영자 해석). 사용자 대화에 대한 이용 정책 책임은 우리에게 있다.
- 크레딧이 떨어지면 API 가 멈출 뿐 Max 요금으로 청구되지 않는다.
- 플랜 하나는 콘솔 조직 하나에만 연결되고, 연결한 조직은 직접 바꿀 수 없다.

### 비용 감
| 모델 | 입력 / 출력 (100만 토큰당) | 한 번(입력 2,000, 출력 300 토큰) | 100달러로 |
|---|---|---|---|
| Haiku 5.5 | 0.10 / 0.50 달러 | 약 0.00035 달러 | 약 28만 번 |
| Sonnet 5.5 | 2 / 10 달러 | 약 0.007 달러 | 약 1만 4천 번 |

### 설계 (결정)
- 모델 **Haiku 5.5.** 대화권 1개 = 질문 1번. (구현 #100: "Haiku 5.5" 라는 모델은 아직 없어 지금 가장 싼 Haiku 인 `claude-haiku-4-5`(입력 1, 출력 5 달러)를 기본으로 두고 서버 설정 `ANTHROPIC_MODEL` 로 바꾼다.) 첫 로그인 선물 10개. **만 18세 이상**이고 로그인한 사람만(기기 계정에 주면 다시 설치로 계속 받을 수 있다).
- 서버가 차감과 호출을 같이 한다. 앱은 API 키를 모른다. 호출이 실패하면 차감을 되돌린다.
- 한 번에 보내는 양: 앱이 최근 대화 몇 개만 보내고, 서버는 입력과 출력 토큰 상한을 건다.
- 서버는 대화 내용을 저장하지 않는다. 사용량 숫자만 남긴다.
- 안전장치: 사람별 하루 상한, 서버 전체 **월 80달러** 상한(넘으면 대화권 대화를 멈추고 내 컴퓨터 AI 로 안내), 콘솔 워크스페이스 지출 상한, 운영자 화면에 사용량.
- 다 쓰면: "대화권을 다 썼어. 내 컴퓨터의 AI 로 이어서 할까?"
- 대화권 늘리기: 이벤트, 쿠폰, 개인 지급. 코인으로 바꾸기는 나중(코인이 서버 정본이라 안전하게 붙일 수 있다).
- **미성년자 조건(Anthropic 확인):** 이용 정책은 18세 미만을 미성년자로 보고, 미성년자가 API 기반 기능과 직접 대화할 수 있는 제품은 "미성년자 대상 조직 지침"과 관련 법을 따르라고 한다. 그 지침에서 반드시(must)인 것은 **사용자에게 사람이 아니라 AI 와 대화 중임을 알리기** 하나다. 권장(should)은 나이 확인, 내용 거르기, 모니터링과 신고 수단, 안전한 사용 안내, Anthropic 아동 안전 시스템 프롬프트, 홈페이지에 준수 사실 공개다. 권장을 요청받고도 안 하거나 위반이 계속되면 계정이 정지될 수 있고, Anthropic 이 주기적으로 점검한다.
- 그래서 대화권 대화에 넣는 것:
  - 대화 창에 "AI 와 대화 중" 표시(필수)
  - 아동 안전 지침을 담은 시스템 프롬프트(Anthropic 제공본이 있으면 그것)
  - 답 하나마다 "신고" 버튼: 신고한 대화만 사용자 동의로 운영자 화면에 올라간다(평소 내용은 저장하지 않음)
  - 출력 길이 상한, 하루 상한(이미 있음)
  - 홈페이지에 안전 조치와 지침 준수 공개(ko, en)
- **만 18세 이상만 쓰게 한다(4판).** Anthropic 이 미성년자로 보는 18세 미만에게는 대화권을 주지 않아 미성년자 대상 지침 부담을 지지 않는다. 위 조치 중 "AI 와 대화 중" 표시, 시스템 프롬프트 안전 지침, 신고 버튼, 상한은 그대로 둔다(인공지능기본법의 생성형 AI 사전 고지에도 맞춘다).
- 18세 미만은 지금처럼 내 컴퓨터 AI(Claude, Codex, Gemini 등)로 대화한다.
- **국외 이전 고지:** 대화권 질문은 Anthropic(미국)으로 간다. 처리방침과 대화권 첫 사용 화면에 이전 항목(질문과 함께 보낸 최근 대화), 국가(미국), 시기와 방법(질문할 때 암호화 전송), 받는 자(Anthropic PBC), 보유기간(Anthropic API 정책상 최대 30일, 정책 위반 조사 등 예외), 거부 방법과 효과(대화권을 쓰지 않으면 이전 없음, 내 컴퓨터 AI 로 대화 가능)를 적는다(제28조의8). Anthropic DPA 상 Anthropic 은 처리자(위탁)다.
- **신고된 대화:** 신고할 때 무엇이 운영자에게 가는지 보여 주고 따로 확인을 받는다. 건강, 가족 이야기 같은 민감정보가 섞일 수 있어 별도 동의로 받는다(제23조). 운영자가 처리하면 30일 안에 지운다. 탈퇴하면 바로 지운다.

### 운영 정책 (2026-10-15, #101 사용자 결정)
- 모델은 Claude Sonnet 5.5(`claude-sonnet-5-5`, $2 / $10 per 1M) (#103 사용자 결정, 전에는 Haiku 5.5). 채팅이라 생각은 끄고(`between_tools`, Sonnet 5.5 는 `disabled` 가 400) effort low, max_tokens 600. 거절(`stop_reason: refusal`)은 서버 거절 폴백(`fallbacks: "default"`)으로 한 번 더 넘기고, 그래도 거절이면 이용권을 되돌리고 안내한다. 모델별 요청 칸은 `server/src/ai-rules.ts` `requestShape` 한 곳. 질문 글자 수 상한은 `AI_MAX_INPUT_CHARS`(기본 8000)이고 운영자 화면에서 더 낮출 수 있다.
- 화면 이름은 "채팅 이용권"(en Chat pass). 1장 = 질문 1번.
- 사람마다 한 달 100번: 허용된 계정에는 매달 1일(한국) "100장까지 채우기"(이월 없음) 정기 지급이 저절로 걸리고 쪽지로 간다. 운영자가 계정마다 바꾸거나 해지한다(해지한 계정에는 다시 걸지 않는다).
- 정기 지급 계정은 100명까지(운영자 화면에서 바꿈). 차면 새 사용자는 403 waitlisted 와 대기 목록.
- 첫 로그인 선물 10장은 기본 꺼짐(운영자가 켤 수 있다). 월 예산은 .env 상한(80달러)을 넘지 못하고, 운영자 화면이 50%, 80% 에서 경고한다.

## 9. 이벤트, 쿠폰, 개인 지급
- 이벤트 종류: 선물(모두에게 코인 n), 배수(기간 동안 출석 또는 집중 코인 x배).
- 이벤트 목록은 운영자 화면에서 만들고, 서버가 홈페이지 정적 파일(`events.json`)로 내보낸다. 앱은 정적 파일만 읽으므로 홈서버 부담이 없고 홈서버가 꺼져도 목록은 보인다.
- 선물 받기는 서버가 계정당 한 번만 보장한다. 배수는 서버가 코인 규칙 확인 때 같이 적용한다.
- 쿠폰: 코드, 코인 또는 대화권 수, 기간, 전체 사용 상한, 계정당 한 번.
- 개인 지급: 운영자가 계정을 골라 코인이나 대화권을 준다. 앱은 다음 맞추기 때 받고 펫이 알린다. 계정은 설정에 보이는 짧은 계정 번호로 찾는다.

### 4단계 구현 (2026-10-15, #101)
- 이벤트는 운영자 화면에서 만들고 서버가 `GET /v1/events.json` 으로 내보낸다. 공개 레포 Actions(`.github/workflows/site-feeds.yml`, 10분마다, 기본 GITHUB_TOKEN 만)가 받아 앱 읽기 코드로 검사(`scripts/site-feeds.mjs`, 하나라도 버리면 실패)하고 바뀌었으면 `site/events.json` 을 main 에 커밋한다. main 보호로 직접 push 가 막히면 `bot/site-feeds` PR 을 연다. 앱은 정적 파일만 읽는다(`src/main/site-events.ts`). 형식과 판단은 `src/shared/site-events.ts`(앱과 서버가 함께 씀).
- 선물 받기 `POST /v1/claim`, 쿠폰 `POST /v1/coupon`: 계정 행 잠금 + 유일 제약(event_claim, coupon_use, coin_entry.entry_id), 쿠폰은 쿠폰 행도 잠가 전체 상한을 지킨다. 합쳐진 계정은 가족 전체로 한 번. 쿠폰 코드는 서버가 만든 12자(30^12)만, 원문 없이 sha256, 틀린 코드 계정당 시간 5번.
- 배수는 맞추기 때 반영한 버는 코인에 (배수 - 1) 만큼을 `boost:<기록 번호>` 한 줄로 더한다. 기록의 날짜(한국 날짜)가 이벤트 기간 안일 때. 하루 상한은 원래 양으로 센다.
- 개인 지급은 쪽지(inbox)로 간다: 보낼 때가 아니라 사용자가 열 때(`POST /v1/inbox/:id/open`) 첨부를 준다. 쪽지는 서버 DB 에 두고 연 쪽지도 이력으로 남긴다(1년 뒤 정리, 탈퇴 시 삭제). `GET /v1/inbox` 는 최근 순 20개, `?before=` 커서.
- 계정의 닉네임(2~12자, `src/shared/account-profile.ts`)과 기기 코드(F-XXXX-XXXX, 무작위, 유일). 운영자는 계정 번호, 기기 코드, 닉네임으로 찾는다.

## 10. 운영자
- 서버의 `/admin` 화면. 운영자 토큰(`x-admin-token`, 상수 시간 비교, daypoll 과 같음).
- 할 수 있는 것: 이벤트, 쿠폰, 개인 지급, 공지와 최소 버전(23절), 계정 찾기(짧은 계정 번호), 코인과 대화권 사용량, 이번 달 AI 비용과 남은 상한.
- 운영자 작업은 모두 기록(누가, 언제, 무엇을)으로 남긴다.
- 구현 (#101): 웹 `/admin` 은 ADMIN_TOKEN 로그인 폼 → `__Host-fairy_admin` 쿠키(HttpOnly, Secure, SameSite=Strict, 30분), 쓰기마다 CSRF 토큰과 같은 출처 검사, 틀린 시도 같은 곳 15분 5번과 전체 20번, CSP `default-src 'none'`, 스크립트 없는 HTML. 앱 안 운영자 칸은 `ADMIN_GOOGLE_SUBS` 의 구글 sub 로그인이 붙은 계정의 세션만(`GET /v1/me` 의 admin, 요청마다 다시 확인). 같은 일을 하는 JSON API `/v1/admin/*` 는 두 인증(쿠키 + x-csrf-token, 운영자 세션 Bearer) 중 하나만 받는다. 모든 쓰기는 같은 트랜잭션에서 `admin_log`.
- 기능 스위치(`feature_flag`, `feature_allow`): 첫 항목 `ai_chat`(off, allowlist, everyone, 기본 allowlist + 운영자 계정). 다음 자리 `kakao_login`.

## 12. 서버 데이터 (초안)
- `account`: 번호, 나이 구분(14세 이상, 18세 이상), 만든 때, 닫힌 때 (표시 이름은 받지 않는다. 앱 안에서 펫이 부르는 이름은 앱에만 둔다)
- `device`: 기기 토큰(해시), 계정
- `login`: 서비스(google, kakao), 계정 고유 번호(sub), 계정. (서비스, sub) 유일
- `coin_entry`: 계정, 앱이 만든 기록 번호(유일), 양, 까닭, 날짜
- `owned_item`: 계정, 물건, 개수
- `ai_ticket`: 계정, 남은 수 / `ai_usage`: 계정, 날짜, 토큰, 비용
- `event`, `event_claim`(계정과 이벤트 유일), `coupon`, `coupon_use`(계정과 쿠폰 유일), `inbox`(쪽지, 개인 지급), `site_doc`(공지 문서), `feature_flag`, `feature_allow`, `ai_setting`, `ai_block`, `ai_waitlist`, `ai_subscription`, `ai_subscription_fill` (0004, #101). `account` 에 `nickname`, `code`
- `backup`: 계정, 파일 위치, 크기, 만든 때 (최근 2개)
- `admin_log`
- IP 는 저장하지 않는다(레이트리밋에만 메모리로 씀).

## 13. 개인정보와 법
- 수집(서버 모드만): 계정 고유 번호(구글 sub, 카카오 회원번호), 나이 구분, 코인과 물건 기록, AI 사용량 숫자, 사용자가 올린 서버 백업, 사용자가 신고한 대화. **표시 이름, 이메일, 전화, 생년월일은 받지 않는다.** 앱 안 모드는 서버로 아무것도 보내지 않는다.
- 근거: 서비스 제공(개인정보보호법 제15조 1항 4호). 민감정보가 섞일 수 있는 서버 백업과 신고 대화는 별도 동의(제23조). 국외 이전(Anthropic)은 위탁으로 처리방침에 공개(제28조의8). 광고, 마케팅 동의 항목은 두지 않는다.
- **만 14세 미만:** 앱은 쓰고 서버 기능은 쓰지 않는다(5절 두 모드). 22절 검토대로 아이의 이용계약을 근거로 보호자 동의 없이 서버 처리를 하는 것은 근거가 불확실하기 때문이다. 보호자 동의 절차가 생기면 다시 연다.
- **만 18세 미만:** AI 대화권은 쓰지 않는다(8절).
- 사업자등록이 없어도 개인정보처리자 의무(처리방침 공개 제30조, 안전성 확보조치 제29조, 파기 제21조, 보호책임자 제31조)는 그대로 진다. 보호책임자는 운영자 본인.
- 보관: 탈퇴 즉시 삭제. 서버 백업은 최근 2개, 1년 미사용 시 삭제. 신고 대화는 처리 후 30일. 운영 기록은 1년.
- 홈페이지 개인정보처리방침(`site/privacy/`)과 이용약관을 2단계에서 고친다(ko, en). 아이도 읽기 쉬운 짧은 판을 함께 둔다.
- 생성형 AI 사용은 대화 창과 처리방침에 미리 알린다(인공지능기본법 제31조, 취미 운영자 적용 여부는 미확정이지만 지킨다).
- 게임산업법: 페어리가 게임물인지, 비영리 등급분류 예외인지는 미확정. 환전 없는 무료 포인트라 경품 규제 근거는 찾지 못했다. 밖에 알리기 전에 게임물관리위원회에 확인한다.
- 사용자가 늘거나 밖에 알리기 전에는 전문가 확인을 받는다.

## 14. 보안
- 비밀(운영자 토큰, Anthropic API 키, OAuth 비밀, DB 비밀번호)은 맥미니 `.env.prod`(chmod 600)와 Actions 시크릿에만. 레포는 공개라 넣지 않는다.
- 앱 쪽 세션과 기기 토큰은 safeStorage 에. 서버는 토큰 해시만 저장.
- 레이트리밋: 기기와 계정 단위, `cf-connecting-ip` 보조.
- 배포 워크플로는 main push 에만 돌고 PR 에서는 시크릿을 쓰지 않는다.
- 한 번만 보장은 DB 유일 제약과 잠금으로(쿠폰 동시 요청 시험 포함).

## 15. 장애와 부담
- 홈서버 한계는 집 인터넷과 전기다. 위 표대로 서버가 꺼져도 앱 기능은 거의 그대로다.
- 감시: 10분마다 `/health`, 세 번 실패하면 GitHub 이슈(daypoll 과 같은 방식).
- 백업: 매일 서버 DB 를 외장 디스크로(daypoll 과 시간을 엇갈리게).
- 부담 감: 이벤트 목록과 공지는 정적 파일이라 0. 코인 맞추기는 사람당 몇 분에 한 번 작은 요청. 실제 일은 AI 중계인데 계산은 Anthropic 이 하고 서버는 글자를 넘겨 줄 뿐이다. 서버 백업은 누를 때만 1~2MB.

## 16. 기술 틀
- fairy 레포 `server/`. NestJS, Postgres, 시작할 때 SQL 마이그레이션, 비 root 컨테이너.
- Docker compose 이름 `fairy`, API `127.0.0.1:3002`, DB 볼륨 `fairy_pgdata`, 로그 상한.
- 노출: 기존 Cloudflare Tunnel 에 `fairy-api.moilga.com` 추가(`fairy.moilga.com` 은 Vercel 홈페이지).
- 배포: `server/**` 가 바뀐 main push 때 Tailscale 로 맥미니에 ssh, 깨끗한 스냅샷으로 빌드, `/health` 확인.
- 앱 패키지에는 들어가지 않는다(`electron-builder.yml` files 는 out, resources, package.json).
- 앱과 서버가 함께 쓰는 규칙(코인, 이벤트 형식)은 `src/shared/` 한 곳에.

## 21. 계정 합치기 규칙
### 언제 합치나
| 경우 | 동작 |
|---|---|
| 기기 계정으로 처음 보는 로그인 | 합치지 않는다. 그 기기 계정에 로그인을 붙인다 |
| 기기 계정으로 이미 있는 계정에 로그인 | 묻지 않고 합친다(기기 계정은 사람이 없는 임시 계정이라 잃을 것이 없다) |
| 로그인한 계정에 다른 서비스를 연결했는데 그 서비스가 이미 다른 계정에 붙어 있음 | 두 계정의 코인과 물건을 보여 주고 "합칠까요?"를 묻는다. 되돌릴 수 없다고 알린다 |

### 무엇을 어떻게
| 항목 | 규칙 |
|---|---|
| 코인 | 더한다. 합치는 쪽 잔액을 "합치기" 한 줄로 남는 쪽에 적는다 |
| 집 단계 | 큰 쪽 |
| 집 모양 | 둘을 합친 모음 |
| 장난감 | 종류마다 큰 쪽 |
| AI 대화권 | 더한다 |
| 같은 이벤트를 둘 다 받음 | 한 번 몫을 코인에서 뺀다(같은 사람이 두 번 받은 것) |
| 같은 쿠폰을 둘 다 씀 | 그대로 둔다(쿠폰은 계정당 한 번이라 서로 다른 계정이었을 때 쓴 것) |
| 출석, 연속 기록, 매주 선물 | 이미 받은 코인은 그대로. 이후 연속 기록은 남는 쪽 기준 |
| 하루 상한 | 합친 날은 두 계정 몫을 넘어도 그대로 둔다 |
| 서버 백업 | 두 계정 것 중 최근 2개만 남긴다 |
| 로그인 연결 | 남는 쪽으로 옮긴다 |
| 기기 토큰 | 남는 쪽을 가리키게 바꾼다(다른 PC 의 앱은 다음 맞추기 때 새 잔액을 받는다) |
| 앱 안 데이터(할 일, 캐릭터) | 건드리지 않는다(서버에 없음) |

- 남는 쪽: 지금 로그인한 계정. 합쳐진 쪽은 닫고 운영 기록에 남긴다.
- 운영자 화면에서 합치기 기록을 볼 수 있다. 되돌리기는 운영자가 손으로(개인 지급으로 보정).

## 23. 공지와 강제 업데이트 (5판)
운영자가 릴리스를 새로 내지 않고도 모든 앱에 공지 창을 띄우고, 필요하면 옛 버전을 잠가 업데이트하게 한다.

### 지금 있는 것
- 강제 업데이트는 이미 있다. 레포의 `release/min-version` 에 버전을 적고 태그를 올리면 릴리스 본문에 `<!-- min-version: x.y.z -->` 가 들어가고, 앱이 GitHub 최신 릴리스를 읽어 잠근다(`src/shared/update-policy.ts` `decideUpdate`, `docs/release.md` "꼭 필요한 업데이트").
- 잠그는 조건: 따로 받은 두 응답이 같은 최소 버전, 최소 버전이 최신 릴리스 이하, 잠금은 `update-lock.json` 에 14일까지 남김. 오프라인이면 잠그지 않는다(보안 장치가 아니라 안내).
- 안내는 펫 말풍선으로 되풀이한다(`src/main/update.ts` `nag`). 공지 창은 없다.
- 한계: 최소 버전을 바꾸려면 새 릴리스를 내야 한다.

- 1.6 단계 (2026-10-15, #91): 공지 파일과 공지 창을 넣었다. 판단은 `src/shared/notices.ts`, 받기는 `src/main/notices.ts`, 창은 `src/main/notice-window.ts`. 강제 안내도 공지 창으로 바뀌었다. 올리는 법은 `docs/release.md` "공지 올리기".

### 바꾸는 것
- **공지 파일:** 홈페이지 정적 파일 `notices.json`(이벤트 목록과 같은 곳, Vercel). 앱은 켤 때와 하루 몇 번 읽는다. 서버도, 계정도 필요 없어 **만 14세 미만 앱 안 모드에서도 똑같이 받는다**(보내는 것 없이 파일만 받는다. GitHub 업데이트 확인과 같다).
- **서버가 꺼져도 된다:** 공지는 홈서버가 아니라 정적 파일에서 읽는다. 운영자 화면이 생기기 전(4단계 전)에는 레포 `site/notices.json` 을 고쳐 main 에 머지하면 홈페이지 배포로 나간다.
- **최소 버전 두 곳:** 앱은 릴리스 본문의 최소 버전과 공지 파일의 `minVersion` 중 높은 쪽을 쓴다. 다만 공지 파일 값도 지금 최신 릴리스 이하여야 잠근다(없는 버전을 요구하면 풀 수 없다). 두 번 받아 같아야 잠그는 규칙도 그대로.
- **공지 창:** 펫 말풍선이 아니라 앱 자체의 작은 창(운영체제 알림이나 시스템 대화 상자 아님). 제목, 본문, 단추 하나 또는 둘.

### 공지 종류
| 종류 | 보이는 때 | 닫기 | 예 |
|---|---|---|---|
| 알림 | 한 번 | 닫으면 끝 | 이번 주 이벤트, 새 기능 |
| 중요 | 켤 때마다, "확인"을 누를 때까지 | 확인을 눌러야 끝 | 장애 안내, 데이터 주의 |
| 업데이트 권장 | 켤 때 한 번, 다음 날 다시 | "나중에" 가능 | 큰 버그 고침 |
| 강제 업데이트 | 최소 버전보다 낮으면 계속 | 닫을 수 없음, "업데이트"만 | 데이터를 망가뜨리는 결함, 보안 |

- 강제 업데이트 창이 떠 있는 동안 멈추는 범위는 지금 잠금과 같다(`updates.locked()` 를 보는 곳). 백업 만들기와 앱 끄기는 반드시 남긴다(데이터를 꺼낼 길).
- 자동 설치가 안 되는 경우(dmg 안에서 실행, 리눅스 등)는 지금처럼 홈페이지 설치 안내를 연다.

### 공지 파일 형식 (초안)
```json
{
  "version": 1,
  "minVersion": "0.4.3",
  "notices": [
    {
      "id": "2026-10-event-1",
      "kind": "info",
      "title": { "ko": "이번 주 선물", "en": "Gift this week" },
      "body": { "ko": "...", "en": "..." },
      "link": "https://fairy.moilga.com/news/1",
      "from": "2026-10-20T00:00:00+09:00",
      "until": "2026-10-27T00:00:00+09:00",
      "versions": "<0.5.0",
      "platforms": ["darwin", "win32"]
    }
  ]
}
```
- `kind`: info, important, update, force. `id` 로 본 공지를 앱에 기록해 다시 띄우지 않는다.
- `versions`, `platforms` 를 비우면 모두에게. 특정 버전에서만 생긴 문제를 그 버전에만 알릴 수 있다.
- 본문은 글자만(HTML 아님). 링크는 홈페이지와 `github.com/milcho0604` 아래만 연다. 그 밖의 주소는 버린다.
- 파일이 깨졌거나, 너무 크거나(64KB 넘음), 모르는 `kind` 면 그 공지만 버린다. 파일 전체를 못 읽으면 아무것도 띄우지 않는다(잘못된 파일로 앱이 잠기지 않게).
- 한 번에 띄우는 공지는 하나. 여럿이면 강제, 중요, 권장, 알림 순으로 차례로.

### 위험과 막는 법
- **공지 파일이 바뀌면 모든 앱이 잠길 수 있다.** 잠그는 값은 최신 릴리스 이하만 믿고, 두 번 받아 같아야 하고, 지금처럼 오프라인이면 잠그지 않는다. 홈페이지 배포 권한(Vercel, 레포 main)은 운영자만.
- **잘못 올린 공지:** 파일을 고치면 다음 읽기 때 사라진다. 이미 닫은 "알림"은 다시 안 뜨므로 정정 공지는 새 `id` 로.
- **너무 자주 뜨기:** 알림과 권장은 하루 한 번까지. 수다 빈도가 "조용히"여도 공지 창은 뜬다(말풍선이 아니라서). 집중 중에는 강제 말고는 집중이 끝난 뒤로 미룬다.
- 개인정보: 앱은 아무것도 보내지 않는다. 홈페이지가 받는 것은 일반 웹 요청(IP 등)뿐이고 저장하지 않는다(Vercel 기본 로그 보관은 처리방침에 적는다).

### 운영자 화면 (4단계)
- 공지 만들기, 미리 보기(ko, en, 창 모양), 기간, 대상 버전과 운영체제, 최소 버전 올리기와 내리기.
- 최소 버전을 올릴 때는 지금 최신 릴리스 번호를 보여 주고 그보다 높으면 막는다. 모든 변경은 운영 기록에 남긴다.
- 저장하면 서버가 `notices.json` 을 홈페이지 정적 파일로 내보낸다(이벤트 목록과 같은 길).
- 구현 (#101): 서버 `GET /v1/notices.json`(한 번도 저장하지 않았으면 404 라 레포 파일을 덮지 않는다) → Actions `site-feeds.yml` → `site/notices.json`. 최소 버전을 올리거나 강제 업데이트 글을 넣을 때는 확인 칸(앱은 두 번 누르기)이 있어야 하고, 최신 릴리스보다 높거나 최신 릴리스를 못 읽으면 올리지 않는다.
