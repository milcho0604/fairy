# 메모에 그림 넣기 기획서

- 판: 2 (2026-11-17). 상태: 적대 검토 반영 뒤, 사용자 결정 대기(코드는 아직 안 고침). 바뀐 것은 맨 끝 「2판에서 바뀐 것」.
- 정하는 것: 메모에 그림을 붙여넣고, 끌어놓고, 단추로 골라 넣는 방법과 그 그림을 저장하고 보여 주고 백업하는 방법. 사용자 말: 「이미지가 안 들어간다 메모에」.
- 바뀌는 문서: 구현 PR 에서 처리방침(`site/privacy`, 8절), `scripts/dev/README.md`. 동기화를 켜는 3단계에서 `docs/sync-plan.md` 와 `docs/server-plan.md` 도 고친다.

## 1. 지금 모습
- 그림 기능이 없다. 마크다운 미리보기는 `![설명](주소)` 를 만나면 주소를 쓰지 않고 설명 글(없으면 "이미지")만 보여 준다(`src/shared/note-markdown.ts:73-77`). 바깥 주소로 요청이 나가면 메모를 연 것이 남에게 알려지기 때문이다(같은 파일 6줄). 이 보장은 그대로 지킨다.
- 미리보기 허용 태그에 `img` 가 없다(`note-markdown.ts:23-52`). DOMPurify 는 `https` 주소만 허용한다(`NoteMarkdown.tsx:44`).
- 창의 CSP 는 `img-src 'self' data:` 라 앱 전용 주소를 못 띄운다(`src/renderer/panel.html:5`, `home.html:5`).
- 편집기는 `textarea` 하나다(`NoteTab.tsx:1050`). 메모 형식은 `txt`(쓴 그대로)와 `md`(미리보기에서 꾸밈)이고, 미리보기 쪽 전환 단추는 `md` 에만 있다(`NoteTab.tsx:465-468`, `1015`).
- 메모 본문은 DB 의 `note.body` 글자뿐이다. 상한 5만 글자(`NOTE_BODY_MAX`, `note-store.ts:53`). 파일을 가리키는 칸이 없다.
- 채팅에는 그림 붙이기가 있다. 붙여넣기(`chat/App.tsx:548`), 크기 줄이기(`chat/images.ts:34-50`, 긴 변 2000px, 3.5MB 넘으면 JPEG, `shared/capture.ts:53-63`), 머리말 검사(`shared/image-head.ts:7-13`, `89`). 이것을 다시 쓴다.

## 2. 원칙
1. **메모 글이 정본이다.** 그림 자리는 본문 글 속의 표기 하나다. DB 표는 바꾸지 않는다(저장 파일 판을 올리지 않는다). 그래서 동기화, 충돌 합치기(`mergeNoteText`, `note-store.ts:112`), MCP, 내보내기가 모두 "글"로 다뤄진다.
2. **바깥으로 요청을 보내지 않는다.** 보이는 그림은 이 컴퓨터의 앱 데이터 폴더 파일뿐이다. `https://` 그림은 지금처럼 설명 글만.
3. **그림 이름은 내용에서 나온다.** 같은 그림은 한 파일. 컴퓨터가 달라도 같은 이름이라 백업, 되살리기, (나중의) 동기화에서 본문을 고칠 필요가 없다.
4. **메인이 마지막에 검사한다.** 창(렌더러)이 보낸 바이트는 믿지 않고 메인이 형식, 크기, 이름을 다시 본다.
5. **글을 잃지 않는다.** 그림 파일이 없어도 메모는 열리고, 자리에 설명 글이 보인다.

## 3. 사용자 동작
### 3-1. 넣는 세 가지 방법
| 방법 | 동작 |
|---|---|
| 붙여넣기 | 편집 칸에서 Cmd/Ctrl+V. 클립보드에 그림 파일이 있고 글이 없으면 그림으로 넣는다(`chat/App.tsx:548-553` 와 같은 판단). 글이 같이 있으면 글만 붙인다 |
| 끌어놓기 | 편집 칸에 그림 파일을 놓는다. 놓는 동안 칸 테두리가 강조된다 |
| 단추 | 편집기 도구 줄(형식 전환 줄, `NoteTab.tsx:1006` 근처)에 "그림 넣기" 단추. 파일 고르기 창은 메인이 연다 |

- 한 번에 여러 장도 된다. 장마다 한 줄씩 넣는다. 그림이 아닌 파일은 무시하고 한 줄로 알린다(채팅과 같은 방식).
- 자리: 글 칸의 커서(고른 글이 있으면 그것을 대신). 앞뒤가 줄 처음과 끝이 아니면 줄바꿈을 더한다.
- 미리보기 중에는 넣을 칸이 없어 단추는 흐리게 두고, 붙여넣기와 끌어놓기는 받지 않는다. 안내 한 줄("편집으로 돌아가서 넣어 줘").
- 작은 패널(폭 320~560)과 큰 창(760~1440)은 같은 `NoteTab` 이라 같은 동작이다. 달라지는 것은 그림의 최대 폭뿐이다(칸 폭 안에서 `max-width: 100%`).

### 3-2. 본문에 들어가는 표기
```
![이미지](fairy-note:3f9a1c0e5b7d42a8c6e01f2d9b8a7c64.png)
```
- 형식: `![설명](fairy-note:<32글자 소문자 16진수>.<png|jpg>)`. 앞 32글자는 저장한 파일 내용의 SHA-256 앞부분이다(`sync-item.ts:46` 의 `bodyHash` 와 같은 길이). 확장자는 저장한 파일 형식이다.
- 설명(alt)은 처음에 "이미지"(`panel.note.mdImage`)로 넣는다. 파일 이름은 쓰지 않는다(이름에 개인 정보가 있을 수 있다). 사용자가 글에서 직접 고치면 된다.
- 이 표기가 글로 남으므로 메모 글을 읽는 모든 곳(검색, 내보내기, MCP, AI 다듬기)이 표기를 만난다. 그곳들은 6절에서 다룬다.

### 3-3. txt 메모와 md 메모
- **md 메모**: 편집 칸에는 표기가 글자로 보이고(`![이미지](fairy-note:...)`), 미리보기에서 그림이 보인다. 지금의 편집/미리보기 전환(`NoteTab.tsx:1015-1030`)을 그대로 쓴다.
- **txt 메모**: 미리보기가 없다(`previewing` 은 `format === 'md'` 일 때만, `NoteTab.tsx:468`). 그림을 보여 줄 곳이 없다. 추천은 **"그림은 마크다운 메모에서만"** 이다. txt 메모에 그림을 넣으려 하면 한 줄 확인("그림을 보려면 마크다운 메모여야 해. 바꿀까?")을 띄우고, 승낙하면 형식을 `md` 로 바꾼 뒤 넣는다(`setFormat`, `note-store.ts:237`. 글은 그대로이고 형식 칸만 바뀌며 동기화되는 칸이다). 거절하면 아무것도 넣지 않는다. 대안(txt 메모 아래에 그림 줄을 따로 두기)은 저장 모양이 둘이 되어 2단계 이후로 미룬다.
- 보이는 글에서 그림 표기는 그대로 `txt` 형식 글처럼 남는다. 나중에 사용자가 `md` 를 `txt` 로 되돌려도 표기는 글자로 남을 뿐 지워지지 않고, 그림 파일도 남는다.

### 3-4. 지울 때, 휴지통, 되살리기
- 본문에서 표기 줄을 지우면 그림이 메모에서 빠진다. 파일은 바로 지우지 않는다(되돌리기와 충돌 사본에 같은 그림이 있을 수 있다). 청소는 4-5절 규칙(마지막 사용 30일, 동기화 켠 계정은 사람이 지움)으로 늦게 한다.
- 메모를 휴지통에 넣으면(`NoteStore.remove`, `note-store.ts:246`, 부르는 곳 `panel.ts:688`, `1446`) 글과 그림 파일 모두 그대로 둔다. 되살리면(`restore`, `note-store.ts:251`) 그림이 그대로 보인다.
- 휴지통을 비우거나(`panel.ts:1128`) 30일이 지나(`panel.ts:1070`) 영구 삭제하면(`purge`, `purgeExpired`, `note-store.ts:279-291`) 그 뒤에 청소를 한 번 돌린다. 다른 메모가 같은 그림을 쓰면 남는다.

## 4. 저장
### 4-1. 자리와 이름
- `<데이터 폴더>/note-images/<32글자>.<png|jpg>`. 한 폴더에 평평하게 둔다(메모 1천 개에 그림 수천 장까지는 문제 없다).
- 쓰기는 `writeFileAtomic`(`main/safe-file.ts:173`), 읽기는 `readFileIn`(`safe-file.ts:42`, 링크를 따라 폴더 밖으로 나가지 않는다)을 쓴다. 이미 같은 이름이 있으면 내용은 다시 쓰지 않는다(같은 내용). 대신 **마지막 사용 기록을 현재로 갱신**한다(4-5절. 안 하면 오래전에 넣은 같은 그림을 다시 붙여도 시각이 옛것이라 청소 대상이 된다).
- 모든 일은 새 메인 파일 `src/main/note-images.ts` 에 모은다. 이름 규칙과 표기 해석은 `src/shared/note-image.ts` 에 두어 렌더러, 메인, 시험이 같이 쓴다.

### 4-2. 허용 형식
- 들어오는 것: PNG, JPEG, WebP, GIF. 머리말로 판단한다. 지금 `imageKind`(`image-head.ts:4-13`)는 gif 를 모르므로(크기 읽기만 GIF 를 안다, `35줄`) `'gif'` 를 더한다.
- **SVG 는 받지 않는다.** 스크립트와 바깥 참조를 품을 수 있고 `<img>` 로 그려도 크기 계산, 글꼴 요청 같은 부작용이 있다. 래스터화 뒤 PNG 로 저장하는 길도 있으나 가치가 작아 넣지 않는다. HEIC, AVIF, TIFF, BMP 도 받지 않는다(안내만).
- 저장하는 것: PNG 아니면 JPEG 둘뿐이다. 창에서 캔버스로 다시 그려 만든다(4-3). 그래서 보이기 쪽은 content-type 이 둘로 끝난다.
- 움직이는 GIF 는 1단계에서 첫 장면 한 장으로 저장한다(캔버스 방식의 한계). 안내 한 줄. 움직임을 지키는 것은 2단계 열린 질문이다.

### 4-3. 크기 상한과 줄이기, EXIF 지우기
- 받는 파일 상한 20MB(읽기 전에 파일 크기부터 본다). 머리말로 본 크기는 `sizeOk`(`image-head.ts:89`, 변 4096, 넓이 1600만 화소)를 통과해야 한다. 풀기 전에 거르는 것이 목적이다(`image-head.ts:1-2` 주석의 큰 그림 사고).
- 채팅과 같은 규칙으로 줄인다: 긴 변 2000px(`capture.ts:53`), PNG 가 3.5MB 를 넘으면 JPEG 90(`capture.ts:55`, `59`, `63`). 채팅용 `toOutgoing`(`chat/images.ts:34-50`)은 작은 그림까지 만들어 쓰임이 달라, 그 안의 `load` 와 `draw` 만 공용 파일로 빼고 메모용 `toNoteImage` 를 따로 만든다.
- **EXIF 와 위치 정보:** 캔버스에 다시 그려 PNG, JPEG 로 새로 부호화하므로 EXIF(GPS, 기기 이름, 촬영 시각)와 PNG 글 조각이 따라오지 않는다. 방향(회전) 값은 브라우저가 그릴 때 이미 반영한다. 시험으로 GPS 가 든 사진을 넣어 저장 파일에 `Exif` 와 GPS 표시가 없는지 확인한다(9절).
- 메인은 받은 바이트를 다시 본다: `imageKind` 가 png 나 jpeg, `sizeOk`, 3.5MB 이하, 이름을 SHA-256 으로 정한다. 하나라도 틀리면 저장하지 않고 이유 코드(`kind`, `big`, `pixels`)를 돌려준다.
- **디코딩 메모리:** 여러 장을 한꺼번에 넣어도 창은 한 장씩 차례로 풀고 줄이고 보낸다(동시 처리 1). 장마다 캔버스를 쓰고 바로 해제한다(`canvas.width = 0`). 메인은 픽셀을 풀지 않고 `imageKind` 와 `sizeOk` 로 머리말만 보며 SHA-256 을 낸다. 즉 메인의 검사는 "창이 보낸 바이트가 PNG/JPEG 로 보이고 크기가 상한 안인가" 까지이고, 실제로 안전하게 풀리는지는 창(렌더러)의 디코더가 맡는 신뢰 경계다. 그래서 변 4096, 1600만 화소 상한을 풀기 전에 건다.
- 메모 하나의 그림 수 상한 30장. 그림 전체 폴더가 1GB 를 넘으면 새로 넣기를 막고 설정의 저장 공간에서 정리하라고 알린다(`keep-copies.ts` 가 이미 그런 칸을 가진 곳. 폴더 크기 줄 하나를 더한다).

### 4-4. 저장 길(창에서 메인으로)
- 창이 줄인 바이트를 IPC 로 보낸다(`PANEL` 채널에 `noteImageSave` 하나, 보낸 창이 우리 창인지 `ours(e)` 로 먼저 본다. `panel.ts:1066` 와 같은 꼴). 메인은 `{ ref }`(표기에 쓸 `<32글자>.<png|jpg>`)를 돌려주고 창이 글 칸에 표기를 넣는다.
- 파일 고르기 창은 메인이 열어 고른 파일을 읽어 같은 검사를 거친다(창에는 경로를 주지 않고 바이트만).
- 글이 저장되기 전에 파일이 먼저 있어야 한다(표기만 있고 파일이 없는 순간을 만들지 않음).

### 4-5. 고아 파일 청소
**왜 1판의 "만든 지 7일" 을 고쳤나.** 동기화는 `note.body` 만 보내고 그림 파일은 보내지 않는다(`src/shared/sync-fields.ts:32` 의 `note` 칸 목록에 그림이 없다). 그래서 다른 기기에서 표기 줄을 지우면 원래 기기는 동기화로 본문이 바뀐 뒤 그 파일이 고아로 보이고 7일 뒤 지워진다. 휴지통은 30일 보관(`src/main/panel.ts:1067-1070` 의 `trashList`, 같은 줄의 로그 "휴지통 30일 지난 항목 영구 삭제")이라 되살리기 기간보다 짧았다. 또 "만든 때" 는 같은 그림을 다시 붙여도 안 바뀐다.

**마지막 사용 기록.** DB 표를 바꾸지 않는 원칙(2절 1)에 따라 파일의 수정 시각(mtime)을 "표기로 마지막에 쓰인 때" 로 쓴다. 새로 저장할 때, 같은 해시가 이미 있어 저장을 건너뛸 때(4-1절), 백업에서 되살릴 때 `utimesSync` 로 현재로 갱신한다. 시각을 못 바꾸는 파일 시스템이면 그 파일은 청소하지 않는다(안전한 쪽). 백업 도구가 시각을 바꿀 수 있다는 점은 한계로 둔다.

**지우는 조건(모두 맞을 때).**
1. 어디에도 안 쓰임: 휴지통 메모를 포함한 모든 메모 본문(동기화 충돌 사본도 `note` 행이라 여기에 든다)과 쓰던 글을 `fairy-note:<이름>` 정규식 하나로 훑어 센다.
2. 마지막 사용 기록으로부터 **30일 이상**. 휴지통 보관 30일과 같거나 길어야 되살린 메모의 그림이 안 사라진다.
3. 가져오기 대기 중이 아님(아래 "복원과 청소").

## 5. 보이기
### 5-1. 앱 전용 주소
- 새 주소 종류 `fairy-note` 를 메인에서 등록한다. **`protocol.registerSchemesAsPrivileged` 는 앱이 준비되기 전에 한 번만 유효하다.** 지금 `maker.ts:118-125` 의 `registerModelScheme` 가 `jj-model` 하나를 등록하는데, 이 호출 말고 한 번 더 부르면 앞의 등록이 덮인다. 그래서 새 등록은 별도 호출이 아니라 **`maker.ts:120-125` 의 기존 목록 배열에 `fairy-note` 항목을 더한다**. 처리기 등록은 `maker.ts:462` 의 `protocol.handle(MODEL_SCHEME, ...)` 와 같은 꼴(앱이 준비된 뒤).
- 특권은 `secure` 정도만 주고 `supportFetchAPI`, `corsEnabled`, `stream` 은 주지 않는다(그림 불러오기만. `jj-model` 은 fetch 가 필요해 `supportFetchAPI: true`, `maker.ts:122`).
- **표기와 주소 모양은 `fairy-note:<이름>`(슬래시 없음) 하나로 정한다.** `fairy-note://<이름>` 은 쓰지 않는다. 호스트 자리에 이름이 들어가면 표준 주소로 정규화되며 호스트가 소문자로 바뀌어 이름 규칙 검사와 대문자 시험이 흔들린다. 본문 표기, `<img src>`, 처리기가 보는 `req.url` 이 모두 같은 모양이다. 확인 필요: 슬래시 없는 주소가 `<img>` 에서 로드되는가(구현 PR 첫 화면 확인). 안 되면 `fairy-note://f/<이름>` 처럼 호스트를 고정하고 이름은 경로로 받는 안으로 간다(그때도 호스트는 `f` 한 글자 소문자라 영향이 없다).
- 처리기는 **디코딩 전과 후 모두** `^[0-9a-f]{32}\.(png|jpg)$` 를 검사한다: 원문 이름이 규칙에 맞아야 하고, `decodeURIComponent` 한 결과도 맞아야 하며 둘이 같아야 한다(`%2e%2e`, `%00`, 이중 인코딩 `%252e`, 대문자 `%41` 이 모두 걸린다). 디코딩이 던지면 404. 맞을 때만 `readFileIn`(`safe-file.ts:42`)으로 읽고 그 밖은 404. 머리말: 맞는 `content-type`(png, jpeg), `X-Content-Type-Options: nosniff`, `Cache-Control: private, max-age=31536000, immutable`(내용 해시라 안 바뀐다).
- **한계 한 줄: 메모 단위 접근 제어는 없다.** 처리기는 "이 창이 이 메모를 볼 권한이 있는가" 를 모른다. 이름(128비트 해시)을 아는 창은 어느 메모의 그림이든 읽는다. 방어선은 해시를 추측할 수 없다는 것과 창별 CSP 이다.
- **어느 창이 요청할 수 있나.** `protocol.handle` 은 세션을 지정하지 않아 기본 세션에 걸린다(앱의 세션 사용은 `src/main/index.ts:271` 의 `session.defaultSession` 뿐이고 `partition` 이나 `fromPartition` 사용은 `grep -rn "partition\|fromPartition" src/main` 에서 나오지 않았다). 따라서 앱의 모든 창이 `fairy-note:` 를 요청할 수 있고, 막는 것은 창별 CSP 의 `img-src` 뿐이다. 창별 실제 값(`src/renderer/*.html`):
  | 창 | `img-src` (지금) | 1단계 변경 |
  |---|---|---|
  | panel.html:5 (패널 메모) | `'self' data:` | `fairy-note:` 더함 |
  | home.html:5 | `'self' data:` | `fairy-note:` 더함 |
  | quick.html:5 (빠른 입력) | `'self' data:` | 그대로. 메모를 안 보여 준다 |
  | chat.html:7 (채팅) | `'self' data: blob:` | 그대로 |
  | settings.html:7 (설정) | `'self' data:` | 그대로 |
  | maker.html:7 | `'self' data: blob:` | 그대로 |
  | knows.html:7, notice.html:7, onboarding.html:7, pet.html:7 | `'self' data:` | 그대로 |
  - `home.html` 이 큰 창의 메모를 그리는지 `panel.html` 이 큰 창과 작은 패널을 함께 그리는지는 **확인 필요**(1판의 "메모가 보이는 두 창" 을 따랐다). 구현 때 두 파일이 불러오는 번들을 열어 확인한다.
### 5-2. 미리보기 변환과 DOMPurify
- `note-markdown.ts` 의 `image` 렌더러(`73-77`): 주소가 `fairy-note:<규칙에 맞는 이름>` 이면 `<img src="..." alt="...">` 를 만든다(`alt` 는 글자 이스케이프). 그 밖의 주소(`https`, `data:`, `javascript:`, `fairy-note:../x` 등)는 지금처럼 설명 글만.
- `MD_ALLOWED_TAGS` 에 `img` 하나만, `MD_ALLOWED_ATTR` 에 `src`, `alt` 를 더한다(`note-markdown.ts:23-62`). `srcset`, `style`, `onerror` 같은 속성은 계속 없다.
- **DOMPurify 처리 순서(소스에서 확인, `node_modules/dompurify/dist/purify.cjs.js`, 3.4.17).** 속성마다 `_sanitizeAttributes`(`:2273`)가 이 순서로 돈다: (1) `uponSanitizeAttribute` 훅(`:2299`), (2) `forceKeepAttr` 면 곧바로 유지(`:2311`), (3) `keepAttr` 가 거짓이면 제거, (4) `_isValidAttribute`(`:2320`)가 `ALLOWED_URI_REGEXP` 로 값을 검사해(`:2164`, 값에서 공백을 먼저 걷어 낸 뒤) 맞지 않으면 속성을 **지운다**. 모든 속성이 끝난 **뒤에야** `afterSanitizeAttributes` 훅이 돈다(`:2329`). 따라서 1판의 "정규식은 그대로 두고 `afterSanitizeAttributes` 에서 `img` 를 본다" 는 틀렸다. `src="fairy-note:..."` 는 정규식(`NoteMarkdown.tsx:44`, `^https?://`)에 걸려 훅이 돌기 전에 이미 지워진다.
- **고친 방법:** `ALLOWED_URI_REGEXP` 를 `https?://` 또는 정확한 `fairy-note:<32 소문자 16진수>.(png|jpg)$` 중 하나로 넓힌다(`i` 플래그는 `https?://` 쪽에만 쓰고 `fairy-note:` 쪽은 소문자만 받아 대문자 `FAIRY-NOTE:` 를 거절한다). 단, 이 검사는 공백을 걷은 문자열로 하므로(`:2164`) 앞 공백이나 줄바꿈이 낀 값도 통과한다. 그래서 `afterSanitizeAttributes` 훅(`NoteMarkdown.tsx:16-33`)에서 `img` 의 `src` 를 **원래 값 그대로**(공백을 걷지 않고) 같은 정확한 정규식으로 다시 검사하고, 안 맞으면 `img` 노드를 지운다. 훅에서 `loading="lazy"`, `decoding="async"` 도 붙인다.
- **`a href`:** 위 정규식을 통과한 `fairy-note:` 값이 `a` 에 오더라도, 훅이 `a` 의 `href` 를 `safeExternalUrl`(`src/shared/links.ts:55-66`)에 넣고, 이 함수는 `https:`, `http:` 가 아니면 `undefined` 를 돌려줘 `href` 를 지운다(`NoteMarkdown.tsx:19-26`). 즉 `a href="fairy-note:..."` 는 걸러진다. 시험으로 고정한다.
- 그림 파일이 없을 때: `img` 의 `error` 에서 설명 글(`alt`)로 바꾼다(`md-image` 클래스, 지금 모양). 접근성으로 `alt` 는 늘 둔다.
- 그림을 눌러 키우기와 복사는 2단계. 1단계는 보기만이고 그림 위 클릭은 링크로 쓰지 않는다.

### 5-3. CSP
- `panel.html:5` 와 `home.html:5`(메모가 보이는 두 창)의 `img-src` 에 `fairy-note:` 하나만 더한다. 나머지 창은 그대로. `connect-src`, `default-src` 는 안 건드린다.
- 시험: 창에서 `https://` 그림 표기를 넣고 네트워크 요청이 0 인지(지금 보장), `fairy-note:` 요청만 보이는지 CDP 의 Network 로 확인한다(9절).

## 7. 백업, 내보내기, 동기화
### 7-1. 내 컴퓨터 백업(`.fairybackup` zip)
- 읽기 규칙은 `entryNameOk`(`src/shared/backup-file.ts:81-90`)가 정한다: 맨 위는 머리 파일과 `topLevel` 에 든 이름만, 한 칸 더 들어간 경로는 `parts[0] === 'pets'` 일 때만 허용한다(`:89`). 1판이 적은 `backup-import.ts:48` 은 없는 파일이고, `backup-zip.ts:48` 은 읽기 규칙이 아니라 이미 눌린 그림을 다시 안 누르는 확장자 목록(`STORED_EXT`)이다. 풀기 쪽 호출은 `backup-zip.ts:241`(머리 파일 목록)과 `:324`(항목)이다. 여기에 `note-images/<규칙에 맞는 이름>` 만 더 허용한다(`parts.length === 2`, `parts[0] === 'note-images'`, 이름이 정규식에 맞을 때).
- 넣기: `petSources`(`backup.ts:108-128`)와 같은 꼴의 `noteImageSources` 로 폴더 안 규칙에 맞는 일반 파일만 모은다(`backup.ts:139-155`). `.png`, `.jpg` 는 다시 안 누른다(`backup-zip.ts:48`).
- **되살릴 때 장당 검사(풀기 전과 후):** (1) 풀린 크기가 장당 상한(3.5MB) 이하(`backup-zip.ts:348` 의 `inflate` 가 `usize` 를 `maxOutputLength` 로 쓰므로 항목 크기를 먼저 본다), (2) `imageKind` 가 png 나 jpeg 만(`gif`, `webp` 는 저장 형식이 아니므로 거절), (3) 파일 이름 앞 32글자가 내용의 SHA-256 앞 32글자와 같음. 하나라도 틀린 항목은 건너뛰고 백업 전체는 거절하지 않는다. 같은 이름이 이미 있으면 덮지 않고 마지막 사용 기록만 현재로 갱신한다(4-5절). 되살려도 `note-images` 의 기존 파일은 지우지 않는다.
- **항목 수 상한:** 지금 항목 5000개(`BACKUP_LIMITS.entries`, `backup-file.ts:23`), 풀린 크기 1GB(`:21`). 그림 한 장이 한 항목이라 그림이 많으면 5000 에 먼저 닿는다. 올리는 안은 **항목 수 2만 + 장당 상한(3.5MB)을 같이 적용**하는 것이다(항목 수만 올리면 작은 파일 수만 개로 느려지는 길이 열린다. 1GB 합계는 그대로). 어느 상한이 맞는지는 열린 질문 8.
- 가져오기 전 안전 복사본(`backup.ts:391` 근처, `keep-copies.ts` 의 `before-import-*`)은 폴더째라 그림이 두 번 쌓인다. 그림은 이름이 내용이라 덮어쓰이지 않으므로 복사본에서 `note-images/` 는 뺀다.
- **서버 백업(20MB, `server-plan.md:131`)**: 처리방침(`site/privacy/index.html:789`)은 서버 백업 파일이 내 컴퓨터 백업과 같다고 적는다. 그림이 들어가면 20MB 를 금방 넘으므로 1단계는 서버 백업에서 그림을 뺀다. 서버 백업에서 되살린 메모는 그림 자리에 설명 글이 보이고, 화면 안내 한 줄과 처리방침 한 줄(8절)로 알린다. 서버 백업이 같은 `exportFile` 을 쓰는지 구현 때 확인한다(확인 필요).

### 7-2. 내보내기(`export.ts`)
- 지금 메모 내보내기는 본문을 그대로 마크다운으로 쓴다(`export.ts:165-209`). 표기 `fairy-note:...` 는 밖의 앱(옵시디언, 메모장)에서 깨진 링크가 된다.
- 그림이 든 메모가 하나라도 있으면 고른 폴더 안에 `images/<이름>` 파일을 같이 쓰고, 본문의 표기를 `![설명](images/<이름>)` 상대 경로로 바꿔 쓴다. "묶음 파일 하나"(`notes-md`)도 같은 폴더 방식이라 `.md` 옆에 `images/` 가 생긴다. 없는 파일은 설명 글로 바꾼다.
- 폴더 쓰기는 `src/main/day-tools.ts:357-362` 에서 한다: `freePath(join(base, 'fairy-memos-<시각>'))` 로 **늘 새 폴더**를 만들어(`mkdirSync`) 그 안에 `writeFileAtomic` 으로 쓴다. 그래서 `images/` 가 미리 있거나 파일, 링크일 수는 없다(새 폴더 안에서 처음 만든다). 다만 메모 파일 이름과 겹치지 않게 `images` 를 예약한다(`noteFileNames` 가 `images` 라는 확장자 없는 이름을 만들 수 없음을 시험으로 고정). 그림 파일은 `readFileIn` 으로 읽어 쓰고 링크는 따라가지 않는다.
- 바꾸는 일은 순수 함수(`noteMarkdown`, `bodyUnderTitle`, `notesMarkdown` 쪽 `166-209`)에 넣어 단위 시험한다. 그림이 한 장도 없으면 지금 결과와 바이트까지 같아야 한다(회귀 시험).

### 7-3. 기기 간 동기화
- 지금 동기화는 항목 덩어리 하나 256KB 이하(`sync-plan.md` 5절), 계정당 합계 100MB, 종류는 `todo`, `todo_step`, `note`, `event`(`sync-fields.ts:4`)다. 메모 본문 칸은 글이라 표기는 이미 동기화된다. 그림 이름이 내용 해시라 컴퓨터마다 같고, 본문을 고칠 필요가 없다. 다른 컴퓨터에는 파일만 없다.
- 형식 전환(txt 를 md 로, 3-3절)의 동기화: `format` 은 `note` 의 동기화 칸(`sync-fields.ts:32`)이고 항목은 칸마다 시각을 가져(`sync-item.ts:186-200` 의 칸별 시계 `c`) 칸별로 합친다. `mergeNoteText`(`note-store.ts:112`)는 본문만 합치고 형식은 다루지 않는다(`format` 은 별도 칸 `setFormat`, `note-store.ts:237`). 그래서 한 기기가 형식을 md 로 바꾸고 다른 기기가 본문을 고치면 칸별로 각각 살아 합쳐진다. 충돌 사본은 원본과 같은 형식을 갖는다(`sync-item.ts:195-196`). 형식 전환 직후 다른 기기에서 txt 로 열린 동안 본문에 표기가 있으면 글자로 보일 뿐 해가 없다. 이 길은 `src/main/sync/note-format.test.ts` 가 이미 시험하므로 거기에 "표기가 든 본문" 한 건을 더한다.
- **1단계 추천: 그림 파일은 보내지 않는다.** 다른 컴퓨터에서는 그림 자리에 설명 글이 보이고 "이 컴퓨터에는 그림이 없어요" 라고 한 줄 알린다. 처리방침도 서버로 가는 것이 늘지 않아 방침 개정 없이 안내 한 줄만 더하면 된다.
- 보내려면 드는 것(3단계 후보):
  | 항목 | 비용 |
  |---|---|
  | 서버 용량 | 그림 한 장 최대 3.5MB 라 100MB 상한에 30장 정도면 찬다. 동기용 그림은 더 줄이거나(긴 변 1600px, 1MB 이하) 계정 상한을 따로 올려야 한다 |
  | 덩어리 | 256KB 상한에 맞춰 장마다 쪼개야 한다(1MB 면 4조각). 새 항목 종류(`note_image`)와 조각 순서, 빠진 조각 처리, 보류 규칙이 필요하다 |
  | 암호화 | 항목마다 AES-256-GCM 으로 잠그는 지금 방식 그대로 쓴다. AAD 에 종류와 uid 가 들어가므로 uid 를 `<해시>` 로 정하면 중복 없이 맞는다. 열쇠 바꾸기(gen 올림) 때 전부 다시 올려야 한다 |
  | 지우기 | 영구 삭제 표식과 90일 뒤 덩어리 비우기를 그림에도 적용할지, 고아 청소와 어떻게 맞출지 정해야 한다. 한 컴퓨터가 지운 파일을 다른 컴퓨터가 아직 쓰는지 알아야 한다 |
  | 처리방침 | 서버로 가는 데이터 종류가 늘므로 개정이 필요하다. 이전 개정과 같은 방식으로 알림 날짜와 시행일을 따로 적고(`site/privacy/index.html:691-693`), `pv.no3`, `pv.srv7`, `pv.sum6` 과 영문(`site/i18n.js`)을 같이 고친다. 홈페이지는 site-prod 로 옮길 때만 배포되므로 기능을 켜기 전에 옮긴다 |
  | 요금과 속도 | 처음 켤 때 그림이 많으면 수십 MB 를 올린다. 진행 표시와 중단이 필요하다 |
- 위 이유로 동기화는 3단계로 미루고 `sync-plan.md` 개정과 같이 한다.

## 8. 개인정보와 문서
- 1단계는 그림이 이 컴퓨터와 내 컴퓨터 백업 파일에만 있고 서버로 가지 않으므로 새 수집은 없다. 다만 처리방침이 서버 백업을 "내 컴퓨터 백업과 같다"고 적고 있어(`site/privacy/index.html:789`) 틀리지 않게 한 줄을 더한다: "메모에 넣은 그림은 서버 백업에 들어가지 않아요". 문구는 ko, en(`site/i18n.js`) 둘 다, 시행일을 바꾼다(알림과 시행 날짜 두 개를 적는 지금 방식).
- `scripts/dev/README.md` 에 새 시험 줄을 더한다.
- 처리방침과 `site` 는 site-prod 로 옮길 때만 배포되므로 앱 릴리스 전에 옮긴다.

### 화면 시험(`scripts/dev/note-images.mjs` 새로)
앱을 `JJ_NO_FOCUS=1 JJ_USER_DATA=<빈 폴더>` 로 맥북 화면에만 띄우고(`scripts/dev/README.md` 방식), 입력은 CDP 로 넣는다. 사람 마우스와 키보드를 쓰지 않는다. `OUT=<레포 밖 폴더> LANG_UNDER_TEST=ko|en`.
- 붙여넣기: 창 안에서 `DataTransfer` 에 그림 파일을 담은 `paste` 이벤트를 보낸다. 끌어놓기도 `drop`. 단추는 메인의 고르기 창을 건너뛰는 시험 손잡이(`__jj`)로 파일 경로를 준다.
- 확인 항목: 표기가 커서 자리에 들어감, 여러 장, txt 메모의 확인 한 줄과 형식 전환, 미리보기에서 그림이 보임, 그림 없는 메모 회귀 없음, 휴지통에 넣고 되살려도 그림이 보임, 파일을 지우면 설명 글이 보임, 바깥 `https://` 그림은 요청 0, 앱 재시작 뒤에도 보임, GPS 가 든 JPEG 를 넣은 뒤 저장 파일에 Exif 와 GPS 없음.
- 폭과 모양: 작은 패널 320, 360, 560, 큰 창 760, 1100, 1440. 가로 넘침(`scrollWidth`) 검사, 아주 넓은 그림과 아주 긴 그림, 밝은 모드와 어두운 모드(투명 PNG 가 어두운 바탕에서 읽히는지), 찍은 화면은 눈으로 본다.
- 동기화 두 앱(`sync-two.mjs`)으로 메모를 맞췄을 때 표기가 그대로 가고 받은 쪽은 설명 글이 보이는지.
- 기존 `note-ready.mjs`, `note-keep.mjs` 가 그대로 통과(단축키와 새 메모 칸 회귀).

## 11. 위험
- 그림이 늘면 디스크가 는다. 한 장 3.5MB 이하, 메모당 30장, 전체 1GB 로 막고 저장 공간에 보인다.
- 고아 청소가 쓰이는 파일을 지우면 그림이 영영 사라진다. 휴지통과 충돌 사본과 쓰던 글까지 세고, 마지막 사용 기록으로부터 30일 여유를 두며, 복원 대기 중에는 건너뛰고, 동기화 켠 계정은 자동 청소를 안 하고, 이름이 낯선 파일은 안 건드린다. 청소 시험을 가장 두껍게 한다.
- 처리기가 파일을 잘못 열면 데이터 폴더 밖이 읽힌다. 이름 규칙 하나뿐이고 경로를 받지 않는다.
- 렌더러가 보낸 바이트 속임수(SVG, 폴리글랏, 작은 파일에 큰 머리말)는 메인 검사로 막는다.
- `img` 를 허용하면 미리보기의 안전이 한 단계 약해진다. `src` 를 정확한 규칙으로만 통과시키고 시험으로 고정한다. 이 파일의 지금 주석(`note-markdown.ts:4-8`)도 같이 고친다.
- 다른 컴퓨터와 서버 백업에서 되살린 메모에는 그림이 비어 있다. 안내가 눈에 띄지 않으면 "그림이 사라졌다" 로 읽힌다.
- 사용자가 본문에서 표기를 직접 지우거나 망가뜨리면 그림은 설명 글이 된다(파일은 마지막 사용 30일 뒤 정리, 동기화 켠 계정은 사람이 지울 때까지).
- 백업 항목 수 상한(5000)을 올리면 가져오기 쪽 방어 한도도 바뀐다. 올린 값으로 느려지지 않는지 보고, 장당 상한을 같이 둔다.
- `registerSchemesAsPrivileged` 는 한 번만 유효하다. 새 주소를 따로 등록하면 `jj-model` 등록을 덮어 모델 받기가 깨진다. 기존 목록에 더한다(5-1절).

## 12. 열린 질문(사용자가 정할 것)
1. txt 메모에 그림을 넣을 때: 확인 뒤 md 로 바꾼다(추천), 그림은 md 에서만 되게 막는다, txt 아래에 그림 줄을 따로 둔다.
2. 움직이는 GIF: 1단계는 첫 장면 한 장(추천), 아니면 움직임을 지키려고 원본 GIF 를 그대로 저장(크기 상한과 EXIF 걸러내기가 복잡해진다).
3. 큰 사진: 지금 채팅과 같은 상한(변 4096, 1600만 화소)이면 최신 휴대폰의 48MP 사진은 거절된다. 그대로 둘지, 8192 변과 6400만 화소로 올리고 메모리를 더 쓸지.
4. 그림 한도: 메모당 30장, 전체 1GB 가 적당한가.
4-1. 고아 청소: 마지막 사용 30일 기준은 확정. 동기화를 켠 계정은 자동 청소를 안 하고 저장 공간 화면에서 사람이 지우는 안(추천)이면 되는지, 아니면 켠 계정도 자동으로 지울지(4-5절 표의 나).
5. 서버 백업: 1단계는 그림을 뺀다(추천). 20MB 상한을 올려서 넣을지는 3단계에서.
6. 동기화로 그림을 보낼지와 시기(3단계 추천). 보낸다면 서버 용량 상한을 더 올려도 되는지.
7. 내보내기: 그림이 있을 때 `.md` 옆에 `images/` 폴더가 생기는 방식이면 되는지(하나의 파일로는 못 담는다).
8. 백업 항목 수 상한 5000 을 2만으로 올리되 장당 상한(3.5MB)과 imageKind, 이름=해시 검사를 같이 거는 안이면 되는지.
9. 편집 칸 모양: 1단계는 표기를 글자로 보이게 둔다. 편집 중에도 그림 축소판을 보고 싶은지(2단계로 미룸).

## 13. 2판에서 바뀐 것
- 고아 청소 기준을 "만든 지 7일" 에서 "마지막 사용 기록(파일 시각)으로부터 30일 이상" 으로. 동기화가 그림을 안 보내(`sync-fields.ts:32`) 다른 기기에서 표기를 지우면 7일 뒤 지워지던 문제. 지우기 전에 휴지통, 충돌 사본, 쓰던 글을 센다. 동기화 켠 계정은 자동 청소를 안 하는 안을 추천(4-5절).
- 쓰던 글: `note-keep.ts` 는 `src/shared/` 에 있고 메인 메모리만이라 메인이 훑을 수 있음(훑기 함수 추가 필요). 파일 나이 30일이 보관 7일보다 김.
- 복원과 청소 경쟁: 복원은 `.import` 로 대기했다 켤 때 반영하므로, 반영 전엔 청소를 건너뛰고 복원과 저장 때 마지막 사용 기록을 현재로.
- 같은 해시가 이미 있어도 마지막 사용 기록을 갱신(4-1절).
- 프로토콜 표기를 `fairy-note:<이름>`(슬래시 없음) 하나로 고정, 디코딩 전후 정규식 검사, 시험 목록 추가, 메모 단위 접근 제어가 없다는 한계, 창별 CSP 표(5-1절).
- 디코딩 메모리: 한 장씩 차례, 메인은 `imageKind` 와 `sizeOk` 만 보는 신뢰 경계(4-3절).
- MCP: 본문 전체 교체 도구는 지금 없음을 확인. 생기면 쓰기 전 기존 표기 보존 검사(6절).
- 백업 근거 줄을 `backup-file.ts:81-90`(읽기 규칙), `backup-zip.ts:48`(눌러 담기 확장자)로 바로잡음. 복원 때도 장당 상한, png/jpeg 만, 이름=해시 검사. 항목 수 상한은 장당 상한과 함께(7-1절).
- DOMPurify: `ALLOWED_URI_REGEXP` 가 `afterSanitizeAttributes` 훅보다 먼저 `src` 를 지우므로 1판 방법이 틀렸다. 정규식에 정확한 `fairy-note:` 를 더하고 훅에서 원래 값을 다시 검사. `a href` 는 `safeExternalUrl` 이 거른다(5-2절).
- 낮은 우선: 형식 전환의 동기화(칸별 시계), 다듬기 자리표 무작위 접두사와 4000자 경계, 내보내기 폴더는 늘 새 폴더, `registerSchemesAsPrivileged` 는 기존 목록에 더함, `writeFileAtomic` 이 폴더 링크를 안 본다는 점.
