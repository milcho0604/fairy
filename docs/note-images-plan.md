# 메모에 그림 넣기 기획서

- 판: 1 (2026-11-17). 상태: 기획 검토 전(코드는 아직 안 고침).
- 정하는 것: 메모에 그림을 붙여넣고, 끌어놓고, 단추로 골라 넣는 방법과 그 그림을 저장하고 보여 주고 백업하는 방법. 사용자 말: 「이미지가 안 들어간다 메모에」.
- 바뀌는 문서: 구현 PR 에서 처리방침(`site/privacy`, 8절), `scripts/dev/README.md`. 동기화를 켜는 3단계에서 `docs/sync-plan.md` 와 `docs/server-plan.md` 도 고친다.

## 1. 지금 모습
- 그림 기능이 없다. 마크다운 미리보기는 `![설명](주소)` 를 만나면 주소를 쓰지 않고 설명 글(없으면 "이미지")만 보여 준다(`src/shared/note-markdown.ts:73-77`). 바깥 주소로 요청이 나가면 메모를 연 것이 남에게 알려지기 때문이다(같은 파일 6줄). 이 보장은 그대로 지킨다.
- 미리보기 허용 태그에 `img` 가 없다(`note-markdown.ts:23-52`). DOMPurify 는 `https` 주소만 허용한다(`NoteMarkdown.tsx:44`).
- 창의 CSP 는 `img-src 'self' data:` 라 앱 전용 주소를 못 띄운다(`src/renderer/panel.html:5`, `home.html:5`).
- 편집기는 `textarea` 하나다(`NoteTab.tsx:1050`). 메모 형식은 `txt`(쓴 그대로)와 `md`(미리보기에서 꾸밈)이고, 미리보기 쪽 전환 단추는 `md` 에만 있다(`NoteTab.tsx:465-468`, `1015`).
- 메모 본문은 DB 의 `note.body` 글자뿐이다. 상한 5만 글자(`NOTE_BODY_MAX`, `note-store.ts:53`). 파일을 가리키는 칸이 없다.
- 채팅에는 그림 붙이기가 있다. 붙여넣기(`chat/App.tsx:548`), 크기 줄이기(`chat/images.ts:34-50`, 긴 변 2000px, 3.5MB 넘으면 JPEG, `shared/capture.ts:53-63`), 머리말 검사(`shared/image-head.ts:7-13`, `89`). 이것을 다시 쓴다.

## 2. 원칙
1. **메모 글이 정본이다.** 그림 자리는 본문 글 속의 표기 하나다. DB 표는 바꾸지 않는다(저장 파일 판을 올리지 않는다). 그래서 동기화, 충돌 합치기(`mergeNoteText`, `note-store.ts:112`), MCP, 내보내기가 모두 "글"로 다뤄진다.
2. **바깥으로 요청을 보내지 않는다.** 보이는 그림은 이 컴퓨터의 앱 데이터 폴더 파일뿐이다. `https://` 그림은 지금처럼 설명 글만.
3. **그림 이름은 내용에서 나온다.** 같은 그림은 한 파일. 컴퓨터가 달라도 같은 이름이라 백업, 되살리기, (나중의) 동기화에서 본문을 고칠 필요가 없다.
4. **메인이 마지막에 검사한다.** 창(렌더러)이 보낸 바이트는 믿지 않고 메인이 형식, 크기, 이름을 다시 본다.
5. **글을 잃지 않는다.** 그림 파일이 없어도 메모는 열리고, 자리에 설명 글이 보인다.

## 3. 사용자 동작
### 3-1. 넣는 세 가지 방법
| 방법 | 동작 |
|---|---|
| 붙여넣기 | 편집 칸에서 Cmd/Ctrl+V. 클립보드에 그림 파일이 있고 글이 없으면 그림으로 넣는다(`chat/App.tsx:548-553` 와 같은 판단). 글이 같이 있으면 글만 붙인다 |
| 끌어놓기 | 편집 칸에 그림 파일을 놓는다. 놓는 동안 칸 테두리가 강조된다 |
| 단추 | 편집기 도구 줄(형식 전환 줄, `NoteTab.tsx:1006` 근처)에 "그림 넣기" 단추. 파일 고르기 창은 메인이 연다 |

- 한 번에 여러 장도 된다. 장마다 한 줄씩 넣는다. 그림이 아닌 파일은 무시하고 한 줄로 알린다(채팅과 같은 방식).
- 자리: 글 칸의 커서(고른 글이 있으면 그것을 대신). 앞뒤가 줄 처음과 끝이 아니면 줄바꿈을 더한다.
- 미리보기 중에는 넣을 칸이 없어 단추는 흐리게 두고, 붙여넣기와 끌어놓기는 받지 않는다. 안내 한 줄("편집으로 돌아가서 넣어 줘").
- 작은 패널(폭 320~560)과 큰 창(760~1440)은 같은 `NoteTab` 이라 같은 동작이다. 달라지는 것은 그림의 최대 폭뿐이다(칸 폭 안에서 `max-width: 100%`).

### 3-2. 본문에 들어가는 표기
```
![이미지](fairy-note:3f9a1c0e5b7d42a8c6e01f2d9b8a7c64.png)
```
- 형식: `![설명](fairy-note:<32글자 소문자 16진수>.<png|jpg>)`. 앞 32글자는 저장한 파일 내용의 SHA-256 앞부분이다(`sync-item.ts:46` 의 `bodyHash` 와 같은 길이). 확장자는 저장한 파일 형식이다.
- 설명(alt)은 처음에 "이미지"(`panel.note.mdImage`)로 넣는다. 파일 이름은 쓰지 않는다(이름에 개인 정보가 있을 수 있다). 사용자가 글에서 직접 고치면 된다.
- 이 표기가 글로 남으므로 메모 글을 읽는 모든 곳(검색, 내보내기, MCP, AI 다듬기)이 표기를 만난다. 그곳들은 6절에서 다룬다.

### 3-3. txt 메모와 md 메모
- **md 메모**: 편집 칸에는 표기가 글자로 보이고(`![이미지](fairy-note:...)`), 미리보기에서 그림이 보인다. 지금의 편집/미리보기 전환(`NoteTab.tsx:1015-1030`)을 그대로 쓴다.
- **txt 메모**: 미리보기가 없다(`previewing` 은 `format === 'md'` 일 때만, `NoteTab.tsx:468`). 그림을 보여 줄 곳이 없다. 추천은 **"그림은 마크다운 메모에서만"** 이다. txt 메모에 그림을 넣으려 하면 한 줄 확인("그림을 보려면 마크다운 메모여야 해. 바꿀까?")을 띄우고, 승낙하면 형식을 `md` 로 바꾼 뒤 넣는다(`setFormat`, `note-store.ts:237`. 글은 그대로이고 형식 칸만 바뀌며 동기화되는 칸이다). 거절하면 아무것도 넣지 않는다. 대안(txt 메모 아래에 그림 줄을 따로 두기)은 저장 모양이 둘이 되어 2단계 이후로 미룬다.
- 보이는 글에서 그림 표기는 그대로 `txt` 형식 글처럼 남는다. 나중에 사용자가 `md` 를 `txt` 로 되돌려도 표기는 글자로 남을 뿐 지워지지 않고, 그림 파일도 남는다.

### 3-4. 지울 때, 휴지통, 되살리기
- 본문에서 표기 줄을 지우면 그림이 메모에서 빠진다. 파일은 바로 지우지 않는다(되돌리기와 충돌 사본에 같은 그림이 있을 수 있다). 청소는 4-5절 규칙으로 늦게 한다.
- 메모를 휴지통에 넣으면(`NoteStore.remove`, `note-store.ts:246`, 부르는 곳 `panel.ts:688`, `1446`) 글과 그림 파일 모두 그대로 둔다. 되살리면(`restore`, `note-store.ts:251`) 그림이 그대로 보인다.
- 휴지통을 비우거나(`panel.ts:1128`) 30일이 지나(`panel.ts:1070`) 영구 삭제하면(`purge`, `purgeExpired`, `note-store.ts:279-291`) 그 뒤에 청소를 한 번 돌린다. 다른 메모가 같은 그림을 쓰면 남는다.

## 4. 저장
### 4-1. 자리와 이름
- `<데이터 폴더>/note-images/<32글자>.<png|jpg>`. 한 폴더에 평평하게 둔다(메모 1천 개에 그림 수천 장까지는 문제 없다).
- 쓰기는 `writeFileAtomic`(`main/safe-file.ts:173`), 읽기는 `readFileIn`(`safe-file.ts:42`, 링크를 따라 폴더 밖으로 나가지 않는다)을 쓴다. 이미 같은 이름이 있으면 쓰지 않는다(같은 내용).
- 모든 일은 새 메인 파일 `src/main/note-images.ts` 에 모은다. 이름 규칙과 표기 해석은 `src/shared/note-image.ts` 에 두어 렌더러, 메인, 시험이 같이 쓴다.

### 4-2. 허용 형식
- 들어오는 것: PNG, JPEG, WebP, GIF. 머리말로 판단한다. 지금 `imageKind`(`image-head.ts:4-13`)는 gif 를 모르므로(크기 읽기만 GIF 를 안다, `35줄`) `'gif'` 를 더한다.
- **SVG 는 받지 않는다.** 스크립트와 바깥 참조를 품을 수 있고 `<img>` 로 그려도 크기 계산, 글꼴 요청 같은 부작용이 있다. 래스터화 뒤 PNG 로 저장하는 길도 있으나 가치가 작아 넣지 않는다. HEIC, AVIF, TIFF, BMP 도 받지 않는다(안내만).
- 저장하는 것: PNG 아니면 JPEG 둘뿐이다. 창에서 캔버스로 다시 그려 만든다(4-3). 그래서 보이기 쪽은 content-type 이 둘로 끝난다.
- 움직이는 GIF 는 1단계에서 첫 장면 한 장으로 저장한다(캔버스 방식의 한계). 안내 한 줄. 움직임을 지키는 것은 2단계 열린 질문이다.

### 4-3. 크기 상한과 줄이기, EXIF 지우기
- 받는 파일 상한 20MB(읽기 전에 파일 크기부터 본다). 머리말로 본 크기는 `sizeOk`(`image-head.ts:89`, 변 4096, 넓이 1600만 화소)를 통과해야 한다. 풀기 전에 거르는 것이 목적이다(`image-head.ts:1-2` 주석의 큰 그림 사고).
- 채팅과 같은 규칙으로 줄인다: 긴 변 2000px(`capture.ts:53`), PNG 가 3.5MB 를 넘으면 JPEG 90(`capture.ts:55`, `59`, `63`). 채팅용 `toOutgoing`(`chat/images.ts:34-50`)은 작은 그림까지 만들어 쓰임이 달라, 그 안의 `load` 와 `draw` 만 공용 파일로 빼고 메모용 `toNoteImage` 를 따로 만든다.
- **EXIF 와 위치 정보:** 캔버스에 다시 그려 PNG, JPEG 로 새로 부호화하므로 EXIF(GPS, 기기 이름, 촬영 시각)와 PNG 글 조각이 따라오지 않는다. 방향(회전) 값은 브라우저가 그릴 때 이미 반영한다. 시험으로 GPS 가 든 사진을 넣어 저장 파일에 `Exif` 와 GPS 표시가 없는지 확인한다(9절).
- 메인은 받은 바이트를 다시 본다: `imageKind` 가 png 나 jpeg, `sizeOk`, 3.5MB 이하, 이름을 SHA-256 으로 정한다. 하나라도 틀리면 저장하지 않고 이유 코드(`kind`, `big`, `pixels`)를 돌려준다.
- 메모 하나의 그림 수 상한 30장. 그림 전체 폴더가 1GB 를 넘으면 새로 넣기를 막고 설정의 저장 공간에서 정리하라고 알린다(`keep-copies.ts` 가 이미 그런 칸을 가진 곳. 폴더 크기 줄 하나를 더한다).

### 4-4. 저장 길(창에서 메인으로)
- 창이 줄인 바이트를 IPC 로 보낸다(`PANEL` 채널에 `noteImageSave` 하나, 보낸 창이 우리 창인지 `ours(e)` 로 먼저 본다. `panel.ts:1066` 와 같은 꼴). 메인은 `{ ref }`(표기에 쓸 `<32글자>.<png|jpg>`)를 돌려주고 창이 글 칸에 표기를 넣는다.
- 파일 고르기 창은 메인이 열어 고른 파일을 읽어 같은 검사를 거친다(창에는 경로를 주지 않고 바이트만).
- 글이 저장되기 전에 파일이 먼저 있어야 한다(표기만 있고 파일이 없는 순간을 만들지 않음).

### 4-5. 고아 파일 청소
- 파일이 어느 메모에서도 안 쓰이면 고아다. 쓰임은 **휴지통 메모를 포함한 모든 메모 본문**, 쓰던 글(`note-keep.ts`, `NoteDraft.tsx` 가 보관하는 것)에서 `fairy-note:<이름>` 을 훑어 센다.
- 지우는 조건은 둘 다 맞을 때: 어디에도 안 쓰임, 그리고 파일을 만든 지 7일이 지남(되돌리기, 방금 붙인 것, 충돌 사본, 다른 컴퓨터에서 온 글이 아직 처리 중일 때를 위한 여유).
- 도는 때: 앱이 켜질 때 한 번(켜짐 직후 무겁지 않게 몇 초 뒤), 영구 삭제 뒤. 본문을 모두 훑는 일이라 메모 5천 개에서도 한 번에 끝나게 표기 정규식 하나로 한다.
- 이름이 규칙에 안 맞는 파일(`note-images` 안의 낯선 파일)은 건드리지 않는다.

## 5. 보이기
### 5-1. 앱 전용 주소
- 새 주소 종류 `fairy-note` 를 메인에서 등록한다(`maker.ts:118-125` 의 `registerSchemesAsPrivileged` 와 `maker.ts:462` 의 `protocol.handle` 와 같은 꼴, 앱이 준비되기 전에 등록). 처리기는 이름이 `^[0-9a-f]{32}\.(png|jpg)$` 에 맞을 때만 `readFileIn` 으로 파일을 읽어 돌려주고, 그 밖에는 404 를 준다. 머리말: 맞는 `content-type`(png, jpeg), `X-Content-Type-Options: nosniff`, `Cache-Control: private, max-age=31536000, immutable`(내용 해시라 안 바뀐다).
- 처리기는 바깥으로 요청하지 않는다. `fetch` 권한(`supportFetchAPI`)은 주지 않는다(그림 불러오기만).
- 표기가 `fairy-note:이름` 형태이고 실제 주소는 `fairy-note://이름` 이어야 하는지(표준 주소 종류 여부)는 구현 PR 에서 화면으로 확인해 정한다. 본문에 저장하는 표기는 `fairy-note:이름` 으로 고정한다.

### 5-2. 미리보기 변환과 DOMPurify
- `note-markdown.ts` 의 `image` 렌더러(`73-77`): 주소가 `fairy-note:<규칙에 맞는 이름>` 이면 `<img src="..." alt="...">` 를 만든다(`alt` 는 글자 이스케이프). 그 밖의 주소(`https`, `data:`, `javascript:`, `fairy-note:../x` 등)는 지금처럼 설명 글만.
- `MD_ALLOWED_TAGS` 에 `img` 하나만, `MD_ALLOWED_ATTR` 에 `src`, `alt` 를 더한다(`note-markdown.ts:23-62`). `srcset`, `style`, `onerror` 같은 속성은 계속 없다.
- `NoteMarkdown.tsx` 는 `ALLOWED_URI_REGEXP` 가 `^https?://` 뿐이라(`44`) `img src` 가 지워진다. 정규식에 `fairy-note:<규칙>` 만 더하지 않고, `afterSanitizeAttributes` 훅(`16-33`)에서 `img` 를 따로 본다: `src` 가 정확히 규칙에 맞지 않으면 노드를 지운다. `loading="lazy"`, `decoding="async"` 를 붙이고, `a` 의 `href` 에 `fairy-note:` 가 오면 이미 `safeExternalUrl` 이 걸러 지우는 동작을 시험으로 고정한다.
- 그림 파일이 없을 때: `img` 의 `error` 에서 설명 글(`alt`)로 바꾼다(`md-image` 클래스, 지금 모양). 접근성으로 `alt` 는 늘 둔다.
- 그림을 눌러 키우기와 복사는 2단계. 1단계는 보기만이고 그림 위 클릭은 링크로 쓰지 않는다.

### 5-3. CSP
- `panel.html:5` 와 `home.html:5`(메모가 보이는 두 창)의 `img-src` 에 `fairy-note:` 하나만 더한다. 나머지 창은 그대로. `connect-src`, `default-src` 는 안 건드린다.
- 시험: 창에서 `https://` 그림 표기를 넣고 네트워크 요청이 0 인지(지금 보장), `fairy-note:` 요청만 보이는지 CDP 의 Network 로 확인한다(9절).

### 5-4. 목록, 제목, 요약 줄
- `previewLine`(`note-store.ts:66-73`)은 `[글](주소)` 를 `글` 로 바꾸지만 앞의 `!` 가 남아 `!이미지` 로 보인다. 그림 표기를 `이미지`(설명)로 바꾸는 규칙을 먼저 두고 시험한다. `noteTitle`(`56-60`)도 본문 첫 줄이 그림뿐이면 같은 글이 된다.
- 검색(`searchNotes`)은 표기 안의 해시를 찾지 않도록 설명 글만 본다.

## 6. 다른 길이 표기를 깨지 않게
| 곳 | 위험 | 규칙 |
|---|---|---|
| MCP 읽기, 덧붙이기 (`mcp-server.ts:546-581`) | AI 가 본문을 읽고 표기를 지우거나 고친다 | 읽기 결과는 그대로 둔다. `add_note`, `append_note` 도구 설명(`489-512`)에 "`![..](fairy-note:..)` 표기는 그대로 둘 것, 그림은 이 도구로 넣을 수 없다" 를 넣는다. 덧붙이기는 끝에 글을 붙일 뿐이라 안전 |
| MCP 로 AI 가 새 표기를 지어 씀 | 존재하지 않는 이름이 나올 수 있다 | 해시를 추측할 수 없고(128비트), 없는 파일은 설명 글로 보이므로 해가 없다. 서버가 쓸 때 막지는 않는다 |
| AI 다듬기 (`note-polish.ts`, 한 번 4000자 `17`) | AI 가 표기를 풀어 쓰거나 지운다 | 보내기 전에 표기를 `[[IMG1]]` 같은 자리표로 바꾸고, 답을 받아 모든 자리표가 한 번씩 그대로 있는지 본 뒤 되돌려 놓는다. 하나라도 빠지면 바꾸지 않고 "그림 표기가 빠져서 적용하지 않았어" 를 알린다. 고른 부분만 다듬을 때(`splicePolished`, `54`)도 같다. 요약, 쪼개기 같이 메모 글을 AI 에 보내는 다른 기능이 있으면 같은 마스킹을 쓴다(구현 때 부르는 곳을 grep 해서 목록으로 확인) |
| AI 답을 메모로 (`chat/App.tsx:1176`) | 답에 `![](https://...)` 가 있다 | 지금처럼 설명 글만 보이고 불러오지 않는다. 시험으로 고정 |
| 세 갈래 합치기 (`mergeNoteText`, `note-store.ts:112`) | 없음 | 글 합치기라 표기가 그대로 산다 |

## 7. 백업, 내보내기, 동기화
### 7-1. 내 컴퓨터 백업(`.fairybackup` zip)
- 읽기 규칙이 맨 위 파일 이름 목록과 `pets/` 아래만 허용한다(`backup-import.ts:48`, `docs/server-plan.md:113`). 여기에 `note-images/` 아래 규칙에 맞는 이름만 더 허용한다.
- 넣기: `petSources`(`backup.ts:108-128`)와 같은 꼴의 `noteImageSources` 로 폴더 안 규칙에 맞는 일반 파일만 모은다(`backup.ts:139-155`). 이미 눌린 그림은 다시 누르지 않는 규칙이 있어(`backup-zip.ts:46`) 그대로 맞는다.
- 상한: 지금 항목 5000개, 풀린 크기 1GB(`server-plan.md:113`). 그림이 많으면 5000 에 먼저 닿는다. 항목 수를 2만으로 올리고 1GB 는 그대로 둘 것을 제안한다(열린 질문).
- 되살리기: 풀 때 파일 이름이 내용의 SHA-256 앞 32글자와 같은지 확인한다(다르면 건너뜀). 같은 이름이 이미 있으면 덮지 않는다. 되살려도 `note-images` 의 기존 파일은 지우지 않는다(청소가 7일 뒤 고아를 정리).
- 가져오기 전 안전 복사본(`backup.ts:391` 근처, `keep-copies.ts` 의 `before-import-*`)은 폴더째라 그림이 두 번 쌓인다. 그림은 이름이 내용이라 덮어쓰이지 않으므로 복사본에서 `note-images/` 는 뺀다.
- **서버 백업(20MB, `server-plan.md:131`)**: 처리방침(`site/privacy/index.html:789`)은 서버 백업 파일이 내 컴퓨터 백업과 같다고 적는다. 그림이 들어가면 20MB 를 금방 넘으므로 1단계는 서버 백업에서 그림을 뺀다. 서버 백업에서 되살린 메모는 그림 자리에 설명 글이 보이고, 화면 안내 한 줄과 처리방침 한 줄(8절)로 알린다. 서버 백업이 같은 `exportFile` 을 쓰는지 구현 때 확인한다(내가 보기엔 같은 만들기 길이나 확인은 구현 PR 몫).

### 7-2. 내보내기(`export.ts`)
- 지금 메모 내보내기는 본문을 그대로 마크다운으로 쓴다(`export.ts:165-209`). 표기 `fairy-note:...` 는 밖의 앱(옵시디언, 메모장)에서 깨진 링크가 된다.
- 그림이 든 메모가 하나라도 있으면 고른 폴더 안에 `images/<이름>` 파일을 같이 쓰고, 본문의 표기를 `![설명](images/<이름>)` 상대 경로로 바꿔 쓴다. "묶음 파일 하나"(`notes-md`)도 같은 폴더 방식이라 `.md` 옆에 `images/` 가 생긴다. 없는 파일은 설명 글로 바꾼다.
- 바꾸는 일은 순수 함수(`noteMarkdown`, `bodyUnderTitle`, `notesMarkdown` 쪽 `166-209`)에 넣어 단위 시험한다. 그림이 한 장도 없으면 지금 결과와 바이트까지 같아야 한다(회귀 시험).

### 7-3. 기기 간 동기화
- 지금 동기화는 항목 덩어리 하나 256KB 이하(`sync-plan.md` 5절), 계정당 합계 100MB, 종류는 `todo`, `todo_step`, `note`, `event`(`sync-fields.ts:4`)다. 메모 본문 칸은 글이라 표기는 이미 동기화된다. 그림 이름이 내용 해시라 컴퓨터마다 같고, 본문을 고칠 필요가 없다. 다른 컴퓨터에는 파일만 없다.
- **1단계 추천: 그림 파일은 보내지 않는다.** 다른 컴퓨터에서는 그림 자리에 설명 글이 보이고 "이 컴퓨터에는 그림이 없어요" 를 눌러 알린다. 처리방침도 서버로 가는 것이 늘지 않아 방침 개정 없이 안내 한 줄만 더하면 된다.
- 보내려면 드는 것(3단계 후보):
  | 항목 | 비용 |
  |---|---|
  | 서버 용량 | 그림 한 장 최대 3.5MB 라 100MB 상한에 30장 정도면 찬다. 동기용 그림은 더 줄이거나(긴 변 1600px, 1MB 이하) 계정 상한을 따로 올려야 한다 |
  | 덩어리 | 256KB 상한에 맞춰 장마다 쪼개야 한다(1MB 면 4조각). 새 항목 종류(`note_image`)와 조각 순서, 빠진 조각 처리, 보류 규칙이 필요하다 |
  | 암호화 | 항목마다 AES-256-GCM 으로 잠그는 지금 방식 그대로 쓴다. AAD 에 종류와 uid 가 들어가므로 uid 를 `<해시>` 로 정하면 중복 없이 맞는다. 열쇠 바꾸기(gen 올림) 때 전부 다시 올려야 한다 |
  | 지우기 | 영구 삭제 표식과 90일 뒤 덩어리 비우기를 그림에도 적용할지, 고아 청소와 어떻게 맞출지 정해야 한다. 한 컴퓨터가 지운 파일을 다른 컴퓨터가 아직 쓰는지 알아야 한다 |
  | 처리방침 | 서버로 가는 데이터 종류가 늘므로 개정이 필요하다. 이전 개정과 같은 방식으로 알림 날짜와 시행일을 따로 적고(`site/privacy/index.html:691-693`), `pv.no3`, `pv.srv7`, `pv.sum6` 과 영문(`site/i18n.js`)을 같이 고친다. 홈페이지는 site-prod 로 옮길 때만 배포되므로 기능을 켜기 전에 옮긴다 |
  | 요금과 속도 | 처음 켤 때 그림이 많으면 수십 MB 를 올린다. 진행 표시와 중단이 필요하다 |
- 위 이유로 동기화는 3단계로 미루고 `sync-plan.md` 개정과 같이 한다.

## 8. 개인정보와 문서
- 1단계는 그림이 이 컴퓨터와 내 컴퓨터 백업 파일에만 있고 서버로 가지 않으므로 새 수집은 없다. 다만 처리방침이 서버 백업을 "내 컴퓨터 백업과 같다"고 적고 있어(`site/privacy/index.html:789`) 틀리지 않게 한 줄을 더한다: "메모에 넣은 그림은 서버 백업에 들어가지 않아요". 문구는 ko, en(`site/i18n.js`) 둘 다, 시행일을 바꾼다(알림과 시행 날짜 두 개를 적는 지금 방식).
- `scripts/dev/README.md` 에 새 시험 줄을 더한다.
- 처리방침과 `site` 는 site-prod 로 옮길 때만 배포되므로 앱 릴리스 전에 옮긴다.

## 11. 위험
- 그림이 늘면 디스크가 는다. 한 장 3.5MB 이하, 메모당 30장, 전체 1GB 로 막고 저장 공간에 보인다.
- 고아 청소가 쓰이는 파일을 지우면 그림이 영영 사라진다. 휴지통과 쓰던 글까지 세고 7일 여유를 두며, 이름이 낯선 파일은 안 건드린다. 청소 시험을 가장 두껍게 한다.
- 처리기가 파일을 잘못 열면 데이터 폴더 밖이 읽힌다. 이름 규칙 하나뿐이고 경로를 받지 않는다.
- 렌더러가 보낸 바이트 속임수(SVG, 폴리글랏, 작은 파일에 큰 머리말)는 메인 검사로 막는다.
- `img` 를 허용하면 미리보기의 안전이 한 단계 약해진다. `src` 를 정확한 규칙으로만 통과시키고 시험으로 고정한다. 이 파일의 지금 주석(`note-markdown.ts:4-8`)도 같이 고친다.
- 다른 컴퓨터와 서버 백업에서 되살린 메모에는 그림이 비어 있다. 안내가 눈에 띄지 않으면 "그림이 사라졌다" 로 읽힌다.
- 사용자가 본문에서 표기를 직접 지우거나 망가뜨리면 그림은 설명 글이 된다(파일은 7일 뒤 정리).
- 백업 항목 수 상한(5000)을 올리면 가져오기 쪽 방어 한도도 바뀐다. 올린 값으로 느려지지 않는지 본다.

## 12. 열린 질문(사용자가 정할 것)
1. txt 메모에 그림을 넣을 때: 확인 뒤 md 로 바꾼다(추천), 그림은 md 에서만 되게 막는다, txt 아래에 그림 줄을 따로 둔다.
2. 움직이는 GIF: 1단계는 첫 장면 한 장(추천), 아니면 움직임을 지키려고 원본 GIF 를 그대로 저장(크기 상한과 EXIF 걸러내기가 복잡해진다).
3. 큰 사진: 지금 채팅과 같은 상한(변 4096, 1600만 화소)이면 최신 휴대폰의 48MP 사진은 거절된다. 그대로 둘지, 8192 변과 6400만 화소로 올리고 메모리를 더 쓸지.
4. 그림 한도: 메모당 30장, 전체 1GB 가 적당한가.
5. 서버 백업: 1단계는 그림을 뺀다(추천). 20MB 상한을 올려서 넣을지는 3단계에서.
6. 동기화로 그림을 보낼지와 시기(3단계 추천). 보낸다면 서버 용량 상한을 더 올려도 되는지.
7. 내보내기: 그림이 있을 때 `.md` 옆에 `images/` 폴더가 생기는 방식이면 되는지(하나의 파일로는 못 담는다).
8. 백업 항목 수 상한 5000 을 2만으로 올려도 되는지.
9. 편집 칸 모양: 1단계는 표기를 글자로 보이게 둔다. 편집 중에도 그림 축소판을 보고 싶은지(2단계로 미룸).
