# 기기 간 동기화 기획서

- 판: 1 (2026-11-02). 상태: 기획 확정, 개발 전.
- 정하는 것: 메모, 할 일, 일정을 여러 컴퓨터에서 맞춰 쓰는 방법. 서버에는 기기에서 잠근 덩어리만 둔다.
- 바뀌는 문서: `docs/server-plan.md` 1절 "하지 않는 것"의 "동기화(백업만 한다)" 를 지우고 이 문서를 가리킨다. 처리방침(`site/privacy`)도 고친다(8절).

## 1. 범위
- 맞추는 것: 메모, 할 일(단계 포함), 일정(반복 포함), 이 셋에 붙은 알림 시각.
- 맞추지 않는 것: 집중 기록, 펫과 나눈 대화, 펫 상태와 그림, 설정, 코인 장부(코인은 이미 서버 정본, server-plan 6절).
- 구글 캘린더와 ics 에서 가져온 일정(`source` 가 google, ics)은 맞추지 않는다. 각 기기가 구글에서 직접 받는다.
- 켜는 조건: 만 14세 이상 서버 계정, 로그인(세션), 사용자가 직접 켬. 기본은 꺼짐.
- 서버 백업(7절)은 그대로 둔다. 동기화는 백업을 대신하지 않는다(지운 것도 맞춰지기 때문).

## 2. 원칙
1. **앱이 정본이다.** 동기화가 꺼지거나 서버가 죽어도 앱은 지금처럼 돈다. 서버에 닿지 않으면 쌓아 두었다가 나중에 보낸다.
2. **서버는 내용을 모른다.** 항목마다 기기에서 AES-256-GCM 으로 잠근 뒤 보낸다. 서버는 덩어리, 번호, 크기, 시각만 안다. 서버가 털려도 내용은 안전하다.
3. **글을 잃지 않는다.** 칸 하나가 양쪽에서 바뀌면 나중 것이 이기되, 메모 본문은 진 쪽을 충돌 사본으로 남긴다.
4. **남의 기기 변경으로 코인이 생기지 않는다.** 다른 기기에서 온 완료는 표시만 바꾸고 코인을 주지 않는다.

## 3. 열쇠와 복구 코드
- 첫 기기에서 켤 때 데이터 열쇠(32바이트 무작위)를 만든다.
- 복구 코드: 무작위 25글자(Crockford base32, 5글자씩 다섯 묶음, 약 125비트). 화면에 한 번 보이고 "적어 뒀어" 를 눌러야 다음으로 간다. 복사와 파일 저장 단추를 둔다.
- 서버에는 복구 코드로 감싼 데이터 열쇠만 둔다: scrypt(복구 코드, 소금) 로 만든 열쇠로 데이터 열쇠를 AES-256-GCM 으로 감싼다. 서버는 소금, scrypt 값, 감싼 열쇠를 보관한다.
- 기기는 데이터 열쇠를 safeStorage 로 잠가 저장한다(서버 토큰과 같은 방식, `src/main/server-secret.ts`). safeStorage 를 못 쓰면 동기화를 켜지 않는다.
- 다른 기기: 로그인 후 동기화를 켜면 복구 코드를 묻는다. 맞으면 감싼 열쇠를 풀어 저장한다. 틀리면 5번까지, 그다음은 1시간 쉰다(서버 제한).
- 복구 코드를 잃었을 때: 동기화가 켜진 기기가 하나라도 있으면 그 기기에서 "복구 코드 새로 만들기" 로 새 코드를 받는다(같은 데이터 열쇠를 새 코드로 다시 감쌈). 기기가 하나도 없으면 서버 사본은 되살릴 수 없다. 각 기기의 데이터는 그대로 남는다.
- 쓰는 도구: Node 내장 `node:crypto` 만. 새 의존성 없음.

## 4. 앱 저장 파일 바꾸기 (24판)
지금은 세 표 모두 정수 번호라 기기마다 겹치고, 할 일과 일정에는 고친 시각이 없다. 24판에서 더한다.
- `uid` 칸: todo, todo_step, note, event 에 무작위 128비트 글자. 기존 행에도 채운다. 유일 색인.
- 칸별 시각 표 `sync_clock(kind, uid, field, t, dev)`: 칸마다 마지막으로 바꾼 시각과 기기.
- 보낼 목록 `sync_outbox(kind, uid)`.
- 영구 삭제 표식 `sync_tomb(kind, uid, t)`: 휴지통 비우기와 30일 만료가 실제 DELETE 라서 다른 기기에 알리려면 따로 남긴다.
- 위 셋은 **SQLite 트리거**로 채운다. 앱과 MCP 서버(별도 프로세스, 같은 파일)가 모두 같은 스토어 클래스를 쓰지만, 트리거면 어느 연결이 써도 빠짐없이 잡힌다. 새 행의 uid 도 트리거가 채운다.
- 다른 기기 변경을 적용할 때는 같은 트랜잭션에서 표식(`app_meta` 의 적용 중 값)을 켜 트리거가 다시 보낼 목록에 넣지 않게 한다.
- 맞추지 않는 칸: `google_hash`, `notified_at`, `auto_removed`, 로컬 번호(id, repeat_of 같은 정수 연결). 정수 연결은 덩어리 안에서 uid 로 바꿔 보낸다.

## 5. 서버
### 표 (마이그레이션 0019_sync.sql)
- `sync_key(account_id pk, salt, params, wrapped, created_at, updated_at)`: 감싼 데이터 열쇠.
- `sync_item(account_id, uid, rev, blob, deleted, updated_at)`, 기본 키 (account_id, uid). blob 은 256KB 이하. 메모 본문 상한이 5만 글자(`NOTE_BODY_MAX`, 한글이면 약 150KB)라서 기기가 잠그기 전에 gzip 으로 줄인다.
- `sync_head(account_id pk, rev)`: 계정마다 1씩 오르는 번호.
- 모두 `account_id ... REFERENCES account(id) ON DELETE CASCADE`. 탈퇴하면 같이 지워진다.
- 종류(메모, 할 일)도 덩어리 안에 넣어 서버가 모르게 한다. 덩어리 길이는 256바이트 단위로 채워 길이로 내용을 짐작하지 못하게 한다.

### API (세션 전용, 기능 키 `sync`)
| 길 | 하는 일 |
|---|---|
| `PUT /v1/sync/key` | 첫 기기가 감싼 열쇠를 올린다. 이미 있으면 409 (코드 새로 만들기는 `rev` 를 같이 보내 덮어쓴다) |
| `GET /v1/sync/key` | 다른 기기가 감싼 열쇠를 받는다 |
| `GET /v1/sync/changes?since=&limit=` | 그 번호 뒤에 바뀐 항목. 한 번에 500개 |
| `POST /v1/sync/push` | 항목 묶음(최대 200개, `uid`, `base`, `blob`, `deleted`). `base` 가 서버의 지금 번호와 같을 때만 받고, 다르면 그 항목만 conflict 로 돌려준다 |
| `DELETE /v1/sync` | 서버 사본과 열쇠를 지운다 |

- 기존 패턴을 따른다: `AuthGuard`, `auth.via === 'session'`, 트랜잭션 안에서 `lockAccount`, `LIMITS` 항목, `{error: '코드'}`.
- 상한: 계정당 항목 10만 개, 합계 100MB. 넘으면 413 `sync_full`, 앱은 "서버 공간이 찼어" 를 보인다. 80%를 넘으면 미리 알린다.
- 상한 근거: 완료한 할 일은 지우지 않고 계속 남는다. 하루 10개씩 5년이면 할 일만 약 1만 8천 개다. 할 일 하나는 잠근 뒤 약 0.5KB 라 10만 개여도 약 50MB, 메모 1천 개(평균 3KB)는 약 3MB 다.
- 기능 키 `sync` 는 처음에 allowlist(운영자와 사용자 계정)로 켠다.
- 계정 합치기(server-plan 21절): 남는 계정의 사본만 둔다. 닫히는 계정의 사본은 지우고, 그쪽 기기는 남는 계정의 복구 코드를 넣은 뒤 자기 항목을 새로 올린다(기기에 데이터가 있으니 잃지 않는다).

## 6. 맞추는 방법
### 흐름
1. 바뀐 것이 생기면 3초 모아서, 또 1분마다, 앱이 앞에 오거나 잠에서 깰 때 돈다.
2. 받기: `changes` 로 새 항목을 받아 풀고, 아래 규칙으로 합쳐 적용한다.
3. 보내기: 보낼 목록의 항목을 잠가 `push`. conflict 가 온 항목은 서버 것을 받아 합친 뒤 다시 보낸다.
4. 닿지 않으면 늦춰 가며 다시 한다. 앱 사용에는 아무 영향이 없다.

### 합치는 규칙
- **칸마다 나중 것이 이긴다.** 칸 시각은 하이브리드 논리 시계(벽시계와 지금까지 본 가장 큰 시각 + 1 중 큰 값)로 정해 기기 시계가 틀려도 순서가 꼬이지 않는다. 같으면 기기 번호로 정한다.
- 예: 집 맥에서 완료, 회사 맥에서 제목 수정이면 둘 다 남는다.
- **메모 본문:** 양쪽이 같은 본문에서 각자 바꿨으면 나중 것을 남기고, 다른 쪽은 새 메모 "제목 (충돌 사본, 기기 이름, 날짜)" 로 만든다. 메모 목록에 "충돌 사본" 표시가 붙는다.
- **지우기:** 휴지통으로 보낸 것(`deleted_at`)은 칸 하나처럼 맞춘다. 한쪽이 지우고 다른 쪽이 고쳤으면 나중 것이 이긴다. 영구 삭제는 삭제 표식으로 맞추며 되살리지 않는다.
- **반복 할 일:** 다음 회차의 uid 를 원본 uid 와 마감 날짜로 정한다. 두 기기가 같은 회차를 따로 만들어도 같은 항목으로 합쳐져 겹치지 않는다.
- **반복 일정:** 앱은 반복 회차를 최소 1년 앞까지 행으로 미리 만든다(`event-store.ts:583`, 최대 730일). 매일 반복 하나가 1년에 365개라 회차를 모두 보내면 금방 상한에 닿는다. 그래서 시리즈 원본(`event_repeat_template`), 건너뛴 회차(`event_repeat_skip`), 사용자가 고친 회차(`user_edited`)만 보낸다. 나머지 회차는 각 기기가 원본에서 다시 만들고, uid 는 시리즈 uid + 시작 시각으로 정해 고친 회차와 겹치지 않게 한다.
- **코인:** 다른 기기에서 온 완료는 표시만 바꾼다. 받은 할 일의 로컬 번호는 지금 규칙(가장 큰 번호와 코인 장부 번호 다음, `todo-store.ts:355`)으로 정해 코인 지문이 겹치지 않게 한다.
- **구글 캘린더:** 내가 만든 일정을 구글로 보낸 기록(`google_id`, `google_cal`, `google_uid`)은 맞춘다. 그래야 다른 기기가 같은 일정을 또 보내거나, 구글에서 다시 받아 둘로 보이지 않는다. 이 부분은 개발 때 두 기기 시험으로 따로 확인한다.

### 처음 켤 때
- 첫 기기: 가진 항목을 모두 올린다.
- 다음 기기: 서버 항목을 받고, 자기 항목도 올린다(합집합). 두 기기가 같은 백업 파일에서 되살린 경우를 위해 처음 한 번만 (종류, 제목, 만든 시각)이 같은 항목을 하나로 합친다.

## 10. 남는 위험
- 복구 코드를 잃고 기기도 모두 잃으면 서버 사본은 끝이다. 화면과 처리방침에 분명히 적는다.
- 반복 일정과 구글 보내기는 지금도 복잡한 곳이라(21판에서 중복 정리 이력) 두 기기 시험을 가장 두껍게 한다.
- 시계가 크게 틀린 기기는 칸 시각이 앞서 나갈 수 있다. 하이브리드 시계와 지금 있는 시계 점프 보호(`clockJumped`)로 줄인다.
