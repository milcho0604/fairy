# 기기 간 동기화 기획서

- 판: 3 (2026-11-02). 상태: 엔진 구현(9절 4번). 2판은 설계 검토(PR #292)를 반영했다: 암호화 규칙, 열쇠 바꾸기, epoch, 칸 트리거 조건, 반복 uid, 코인, 구글 id, 메모 충돌 사본 uid. 3판은 엔진을 만들며 정한 것을 반영했다(고친 곳에 `(3판)` 표시): 암호화 AAD 의 계정 값, 같은 시각 칸의 승부, 메모 base, 보류와 고아, 로그아웃, 되살리기, `auto_removed`.
- 정하는 것: 메모, 할 일, 일정을 여러 컴퓨터에서 맞춰 쓰는 방법. 서버에는 기기에서 잠근 덩어리만 둔다.
- 바뀌는 문서: `docs/server-plan.md` 1절 "하지 않는 것"의 "동기화(백업만 한다)" 를 지우고 이 문서를 가리킨다. 처리방침(`site/privacy`)도 고친다(8절).

## 1. 범위
- 맞추는 것: 메모, 할 일(단계 포함), 일정(반복 포함), 이 셋에 붙은 알림 시각.
- 맞추지 않는 것: 집중 기록, 펫과 나눈 대화, 펫 상태와 그림, 설정, 코인 장부(코인은 이미 서버 정본, server-plan 6절).
- 구글 캘린더와 ics 에서 가져온 일정(`source` 가 google, ics)은 맞추지 않는다. 각 기기가 구글에서 직접 받는다.
- 켜는 조건: 만 14세 이상 서버 계정, 로그인(세션), 사용자가 직접 켬. 기본은 꺼짐.
- 서버 백업(7절)은 그대로 둔다. 동기화는 백업을 대신하지 않는다(지운 것도 맞춰지기 때문).

## 2. 원칙
1. **앱이 정본이다.** 동기화가 꺼지거나 서버가 죽어도 앱은 지금처럼 돈다. 서버에 닿지 않으면 쌓아 두었다가 나중에 보낸다.
2. **서버는 내용을 모른다.** 항목마다 기기에서 AES-256-GCM 으로 잠근 뒤 보낸다. 서버는 덩어리, 번호, 크기, 고친 시각, 지움 여부만 안다. 서버가 털려도 복구 코드가 안전하면 내용은 안전하다.
3. **글을 잃지 않는다.** 칸 하나가 양쪽에서 바뀌면 나중 것이 이기되, 메모 본문은 진 쪽을 충돌 사본으로 남긴다.
4. **남의 기기 변경으로 코인이 생기지 않는다.** 다른 기기에서 온 완료는 표시만 바꾸고 코인을 주지 않는다.

## 3. 열쇠와 복구 코드
- 첫 기기에서 켤 때 데이터 열쇠(32바이트 무작위)를 만든다.
- 복구 코드: 무작위 25글자(Crockford base32, 5글자씩 다섯 묶음, 약 125비트). 화면에 한 번 보이고 "적어 뒀어" 를 눌러야 다음으로 간다. 복사와 파일 저장 단추를 둔다.
- 감싸기: scrypt(복구 코드, 소금) 로 만든 열쇠로 데이터 열쇠를 AES-256-GCM 으로 감싼다. **서버는 소금, scrypt 매개변수(N, r, p), 감싼 열쇠만 보관한다. 복구 코드와 파생 열쇠는 어떤 경우에도 기기 밖으로 나가지 않는다.** 기기는 서버가 준 매개변수를 허용 범위(N 은 2^17 이하)일 때만 쓴다.
- 감싼 열쇠의 AAD 는 `fairy-sync-key|account_id|gen|params|소금`. (3판) 앱은 서버의 숫자 계정 번호를 보지 못한다(`GET /v1/me` 도 주지 않는다). 그래서 `account_id` 자리에는 서버가 정해 준 계정 코드(`F-XXXX-XXXX`, 계정마다 유일하고 바뀌지 않는다)를 쓴다. `params` 는 `N,r,p` 로 적고 소금은 base64 글자 그대로 넣는다. 열쇠 감싸기는 scrypt 를 비동기로 돌려 메인 프로세스를 막지 않는다.
- 항목 잠그기: nonce 는 잠글 때마다 `randomBytes(12)` 로 새로 만들어 덩어리 앞에 붙인다(여러 기기가 같은 열쇠를 쓰므로 카운터 nonce 는 쓰지 않는다). AAD 는 `fairy-sync-v1|account_id|uid|gen`. 푼 뒤 안쪽 uid 와 종류가 바깥과 같은지 확인한다. 서버가 덩어리를 다른 uid 로 바꿔치기하면 풀리지 않는다. (3판) 평문은 `{kind, uid, v:1, ...}` JSON 을 gzip 한 것에 4바이트 길이를 앞에 붙이고 0 으로 채워 256바이트의 배수로 만든 것이다(gzip 뒤 채움은 풀 때 끝을 알 수 없어 길이를 둔다). 푼 글의 크기는 16MB 로 막는다.
- 기기는 데이터 열쇠를 safeStorage 로 잠가 저장한다(서버 토큰과 같은 방식, `src/main/server-secret.ts`). safeStorage 를 못 쓰면 동기화를 켜지 않는다. (3판) 열쇠 파일은 `sync-key.json`. 켜짐, 기기 번호, 커서, epoch, gen, key_rev, 계정은 저장 파일 밖 `sync-state.json` 에 둔다(`server-state.json` 안에 넣지 않았다: 그 모양을 바꾸지 않으려고). 둘 다 백업에 넣지 않는다.
- 첫 기기의 저장 순서: `PUT /v1/sync/key` 가 성공한 뒤에만 데이터 열쇠를 기기에 저장한다. 409(다른 기기가 먼저 켬)면 만든 열쇠를 버리고 "복구 코드 넣기" 로 간다. (3판) 올릴 때 기기가 아는 epoch 는 처음 0 이다. 서버 사본을 지운 계정은 head 줄이 남아 epoch 가 0 이 아니므로, 409 `epoch` 가 준 값으로 한 번 더 올린다.
- 다른 기기: 로그인 후 동기화를 켜면 복구 코드를 묻는다. 감싼 열쇠를 받아 기기에서 풀고, 풀리면 저장한다. 맞는지는 기기만 알 수 있어서 서버가 틀린 횟수를 셀 수 없다. 대신 복구 코드가 약 125비트라 감싼 열쇠를 가져가도 맞혀 볼 수 없다. 감싼 열쇠는 로그인한 본인 세션에만 준다.
- 기기에서 열쇠가 사라졌을 때(키체인 초기화, 다시 설치): 서버에 열쇠가 있으면 첫 기기로 보지 않고 "복구 코드 넣기" 로 간다. 새 열쇠를 만들어 덮지 않는다.
- 두 가지 동작을 나눈다.
  - **복구 코드 새로 만들기**(코드를 잃었을 때): 같은 데이터 열쇠를 새 코드로 다시 감싼다(`key_rev` +1). 옛 코드와 옛 감싼 열쇠를 가진 사람은 여전히 풀 수 있다고 화면에 적는다.
  - **열쇠 바꾸기**(코드가 샜을 때): 새 데이터 열쇠를 만들고 세대(`gen`)를 1 올린다. 서버는 그 계정 항목을 모두 지우고, 기기가 새 열쇠로 다시 올린다. 서버는 옛 세대의 push 를 받지 않는다.
- 기기가 하나도 남지 않고 복구 코드도 잃으면 서버 사본은 되살릴 수 없다. 각 기기의 데이터는 그대로 남는다.
- 쓰는 도구: Node 내장 `node:crypto` 만. 새 의존성 없음.

## 4. 앱 저장 파일 바꾸기 (24판)
지금은 세 표 모두 정수 번호라 기기마다 겹치고, 할 일과 일정에는 고친 시각이 없다. 24판에서 더한다.
- `uid` 칸: todo, todo_step, note, event 에 128비트 글자. 기존 행에도 채운다. 유일 색인. 새 행은 무작위이고, 정해진 규칙으로 만드는 행(반복 회차, 충돌 사본)은 6절의 결정적 uid 를 쓴다.
- 칸별 시각 표 `sync_clock(kind, uid, field, t)`: 칸마다 마지막으로 바꾼 시각.
- 보낼 목록 `sync_outbox(kind, uid)`.
- 영구 삭제 표식 `sync_tomb(kind, uid, t)`: 휴지통 비우기와 30일 만료가 실제 DELETE 라서 다른 기기에 알리려면 따로 남긴다.
- 위 셋은 **SQLite 트리거**로 채운다. 앱과 MCP 서버(별도 프로세스, 같은 파일)가 모두 같은 스토어 클래스를 쓰지만, 트리거면 어느 연결이 써도 빠짐없이 잡힌다.
- 칸 트리거는 모두 `WHEN old.칸 IS NOT new.칸` 일 때만 그 칸 시각을 올린다. 지금 `event-store` 와 `note-store` 의 update 는 바뀌지 않은 칸도 늘 다시 쓰기 때문에, 이 조건이 없으면 칸마다 맞추기가 행마다 맞추기로 무너진다.
- 기계적 갱신(24판의 uid 채우기, `repeat_clock` 보정, 시간대 보정, 시계 점프 보정, 구글 보내기 기록 초기화)은 칸 시각을 올리지 않는다.
- 다른 기기 변경을 적용할 때는 같은 트랜잭션 안에서만 `app_meta` 의 적용 중 표식을 켜고 끈다. 앱이 저장 파일을 열 때 남은 표식이 있으면 지운다(표식이 남으면 이후 편집이 영영 안 보내진다).
- 기기 번호와 받은 번호(커서)는 저장 파일 밖(서버 상태 파일)에 둔다. 백업을 되살리면 저장 파일이 통째로 바뀌므로, 되살린 뒤에는 기기 번호를 새로 만들고 커서를 0 으로 돌려 전부 다시 받는다. (3판) 항목마다 서버에서 마지막으로 본 번호(`sync_seen`), 보류(`sync_hold`), 충돌 사본 표시(`sync_copy`)는 트리거 대상이 아닌 기계적 표라 저장 파일 안에 두고, 엔진이 `create table if not exists` 로 만든다(판을 올리지 않는다).
- 맞추지 않는 칸: id, `sort_ord`(순서는 기기마다), `google_id`, `google_cal`, `google_uid`, `google_hash`, `notified_at`, `remind_min`, `coins`. (3판) `auto_removed`(되돌리기가 걷어 낸 다음 회차)는 `deleted_at` 과 함께 간다: 덩어리에 값을 싣고 칸 시각은 `deleted_at` 것을 그대로 쓴다. 안 보내면 걷어 낸 회차가 다른 기기 휴지통에 사람이 지운 것처럼 보인다. `remind_min` 은 받은 알림 목록에서 정한다. 정수 연결(repeat_of, todo_id, repeat_series)은 덩어리 안에서 uid 로 바꿔 보낸다.
- 알림(`reminder` 표)은 부모 할 일이나 일정의 `reminders` 칸으로 보낸다. 지금 `set` 은 지우고 다시 넣으므로 부모 uid 로 보낼 목록에 넣는다.

## 5. 서버
### 표 (마이그레이션 0019_sync.sql)
- `sync_key(account_id pk, salt, params, wrapped, gen, key_rev, created_at, updated_at)`: 감싼 데이터 열쇠.
- `sync_item(account_id, uid, rev, blob, deleted, updated_at)`, 기본 키 (account_id, uid). blob 은 256KB 이하. 메모 본문 상한이 5만 글자(`NOTE_BODY_MAX`, 한글이면 약 150KB)라서 기기가 잠그기 전에 gzip 으로 줄인다.
- `sync_head(account_id pk, rev, epoch, items, bytes, last_access_at)`: 계정마다 1씩 오르는 번호, 초기화 횟수, 사용량.
- 모두 `account_id ... REFERENCES account(id) ON DELETE CASCADE`. 탈퇴하면 같이 지워진다.
- 종류(메모, 할 일)도 덩어리 안에 넣어 서버가 모르게 한다. 덩어리 길이는 256바이트 단위로 채운다(길이를 조금 가릴 뿐 완전히 숨기지는 못한다).
- 서버 로그와 오류 응답에 덩어리와 uid 를 남기지 않는다.

### API (세션 전용, 기능 키 `sync`)
| 길 | 하는 일 |
|---|---|
| `PUT /v1/sync/key` | 처음이면 저장. 있으면 `key_rev` 가 같을 때만 덮어쓴다(아니면 409). `gen` 이 오르면 그 계정 항목을 모두 지운다 |
| `GET /v1/sync/key` | 다른 기기가 감싼 열쇠를 받는다. 없으면 404 |
| `GET /v1/sync/status` | 켜짐, 항목 수, 크기, 상한, 곧 지워짐 |
| `GET /v1/sync/changes?since=&limit=&epoch=` | 그 번호 뒤에 바뀐 항목. 한 번에 500개 |
| `POST /v1/sync/push` | 항목 묶음(최대 200개, `uid`, `base`, `blob`, `deleted`, 묶음의 `epoch`). `base` 가 서버의 지금 번호(없으면 0)와 같을 때만 받고, 다르면 그 항목만 conflict 로 지금 것을 돌려준다 |
| `DELETE /v1/sync` | 서버 사본과 열쇠를 지운다 |

- **epoch:** 서버 사본 지우기, 계정 합치기, 열쇠 바꾸기 때마다 1 오른다. 모든 응답에 `epoch` 와 `gen` 을 담고, `changes` 와 `push` 는 기기가 가진 epoch 가 다르면 409 `epoch` 로 거절한다. 열쇠가 없으면 push 는 409 `no_key`. 기기는 이걸 받으면 맞추기를 멈추고 커서를 지운 뒤 "복구 코드를 다시 넣어 줘" 를 보인다. 낡은 열쇠나 커서로 계속 올리는 일을 막는다.
- `push` 본문은 덩어리가 커서 전역 JSON 상한(256KB, `app.ts`)보다 먼저 이 길 전용 파서를 달아 4MB 로 둔다. `Content-Length` 가 넘으면 413. 덩어리는 base64 를 푼 뒤 256KB 로 잰다. 앱은 묶음 합이 4MB 를 넘지 않게 나눈다.
- 기존 패턴을 따른다: `AuthGuard`, `auth.via === 'session'`, 트랜잭션 안에서 `lockAccount`, `LIMITS` 항목, `{error: '코드'}`. 상한 검사와 번호 올리기도 같은 트랜잭션에서 한다.
- 상한: 계정당 항목 10만 개, 합계 100MB. 넘으면 묶음 전체를 413 `sync_full` 로 거절하고, 앱은 "서버 공간이 찼어" 를 보인다. 80%를 넘으면 미리 알린다.
- 지운 항목도 행을 남긴다(다른 기기에 알려야 하므로). 90일이 지나면 서버가 덩어리만 비우고(uid 와 번호는 남김) 그때부터 상한에서 뺀다.
- 상한 근거: 완료한 할 일은 지우지 않고 계속 남고, 단계도 회차마다 복사된다. 하루 할 일 10개에 단계 몇 개면 5년에 약 3만 개다. 항목 하나는 잠근 뒤 약 0.5KB 라 10만 개여도 약 50MB, 메모 1천 개(평균 3KB)는 약 3MB 다.
- 기능 키 `sync` 는 처음에 allowlist(운영자와 사용자 계정)로 켠다.
- 계정 합치기(server-plan 21절): 합치기는 계정 행을 지우지 않고 닫으므로(`accounts.ts`, `closed_at`, `merged_into`) CASCADE 가 돌지 않는다. `merge()` 트랜잭션 안에서 닫히는 계정의 sync 표를 직접 지우고 남는 계정의 epoch 를 올린다. 그쪽 기기는 남는 계정의 복구 코드를 넣은 뒤 자기 항목을 새로 올린다(기기에 데이터가 있으니 잃지 않는다).

## 6. 맞추는 방법
### 흐름
1. 바뀐 것이 생기면 3초 모아서, 또 1분마다, 앱이 앞에 오거나 잠에서 깰 때 돈다.
2. 받기: `changes` 로 새 항목을 받아 풀고, 아래 규칙으로 합쳐 적용한다.
3. 보내기: 보낼 목록의 항목을 잠가 `push`. conflict 가 온 항목은 서버 것을 받아 합친 뒤 다시 보낸다. 같은 항목은 한 번 돌 때 3번까지만 다시 보낸다.
4. 닿지 않으면 늦춰 가며 다시 한다. 앱 사용에는 아무 영향이 없다.
5. 풀리지 않거나 적용에 실패한 항목은 그 항목만 따로 두고(보류) 나머지는 계속한다. 한 항목이 전체 맞추기를 멈추지 않게 한다. 보류 항목 수는 상태 줄에 보인다. (3판) 보류 까닭은 `decrypt`(풀지 못함), `apply`(적용 실패), `parent`(부모가 아직 안 옴), `big`(덩어리가 256KB 를 넘어 못 보냄)이다. `parent` 는 받기가 끝날 때마다 다시 적용하고, 10분이 지나도 앞 회차나 시리즈 원본이 없는 할 일과 일정은 반복 연결만 끊고 적용한다. 서버가 아는 항목인데 행이 없으면(영구 삭제됨) 기다리지 않는다: 연결만 끊고 쓰고, 단계는 쓰지 않고 서버에도 삭제 표식을 올린다. 요청 한도(429)를 만나면 1분을 쉰다(받은 곳까지는 커서에 남는다).
6. (3판) 보내는 순서: 할 일과 메모, 반복 일정 원본, 일정 회차, 단계. 부모가 먼저 가야 받는 쪽이 보류하지 않는다. 묶음은 항목 200개, 덩어리 합 3.5MB 로 나눈다.

### 상태는 계정에 묶는다
- 켜짐, 데이터 열쇠, 커서, 기기 번호는 account_id, gen, epoch 와 함께 둔다. 셋 중 하나라도 서버와 다르면 멈춘다.
- 로그아웃, 탈퇴, 다른 계정으로 로그인, 서버 사본 지우기 때는 데이터 열쇠와 커서를 지운다. 같은 컴퓨터에서 다른 사람이 로그인했을 때 앞사람 메모가 새 계정으로 올라가지 않게 한다. (3판) 로그아웃과 탈퇴는 동기화를 끈 상태로 둔다(열쇠가 없으니 다시 켜서 복구 코드를 넣어야 한다). 세션이 만료되어 로그인만 풀린 것은 켜진 채 기다린다(상태 `login`). 로그인한 계정 코드가 켠 계정과 다르면 열쇠와 커서를 지우고 끈다(상태 `account`). epoch 나 gen 이 서버와 다르면 열쇠와 커서를 지우고 켜진 채 "복구 코드 넣기" 상태로 멈춘다(`epoch`, `gen`).
  - (3판) 마지막으로 맞춘 계정 코드(`lastAccount`)는 로그아웃해도 `sync-state.json` 에 남긴다. 켤 때 그 값이 있고 지금 계정과 다르면 이 컴퓨터 항목을 자동으로 올리지 않고 `askUpload` 로 멈춘다. 고르는 것은 `uploadLocal()`(이 컴퓨터 항목을 이 계정에 올림)과 `downloadOnly()`(서버 것만 받음: 기존 항목은 `sync_skip` 표시를 남겨 다시 올리지 않고, 이후 새로 고친 항목은 올라간다). 값이 없는 컴퓨터(처음 켬)와 같은 계정으로 다시 켠 컴퓨터는 묻지 않고 올린다.
  - (3판) 열쇠 보관은 순서를 지킨다: 첫 기기는 올린 뒤 저장이 안 되면 서버 열쇠를 지워 되돌리고(지우지도 못하면 코드를 돌려줘 적어 두게 한다), 열쇠 바꾸기는 새 열쇠를 먼저 저장해 두고(안 되면 올리지 않는다) 올리다 실패하면 옛 열쇠로 되돌린다. 복구 코드 새로 만들기와 열쇠 바꾸기는 서버의 epoch 가 이 기기가 아는 값과 다르면 서버 열쇠를 건드리지 않고 멈춘다(서버의 감싼 열쇠는 옛 복구 코드로 감싼 것이라 이 기기에서 풀어 비교할 수 없다). 켜는 중에 계정이 끝나면(로그아웃) 돌아온 결과를 버린다.
  - (3판) 반복 연결(`repeat_of`, `repeat_series`)이 가리키는 부모의 uid 는 `sync_idmap`(번호와 uid)에 적어 둔다. 부모를 영구 삭제해도 자식이 보내는 값이 기기마다 같다. 부모가 없어 끊고 쓴 연결은 칸 시각을 올리지 않고 `sync_link` 에 원래 부모 uid 를 남겨 두었다가, 그 uid 의 부모가 적용되면 다시 잇는다.

### 합치는 규칙
- **칸마다 나중 것이 이긴다.** 칸 시각은 하이브리드 논리 시계(벽시계와 지금까지 본 가장 큰 시각 + 1 중 큰 값)로 정해 기기 시계가 조금 틀려도 순서가 꼬이지 않는다. 같으면 (3판) 값의 정해진 글자 순서(키를 정렬한 JSON 글자 비교)로 큰 쪽이 이긴다. 기기 번호로 정하려면 칸마다 쓴 기기를 저장 파일에 더 적어야 하는데, 값 순서도 어느 기기에서 합쳐도 같은 쪽이 남아 수렴한다. 기기 번호와 이름은 덩어리에 싣되 충돌 사본 제목에만 쓴다.
- 받은 칸 시각이 지금보다 하루 넘게 앞서면 지금 + 1일로 잘라 쓴다. 시계가 크게 틀린 기기 하나가 모든 기기의 시계를 미래로 끌고 가지 않게 한다.
- 예: 집 맥에서 완료, 회사 맥에서 제목 수정이면 둘 다 남는다.
- **메모 본문:** 항목마다 마지막으로 맞춘 본문의 지문(base)을 둔다. 양쪽 모두 base 와 다를 때만 충돌이다. 먼저 이미 있는 세 갈래 합치기(`mergeNoteText`, `note-store.ts:103`)를 써 보고, 안 합쳐지면 나중 것을 남기고 진 쪽을 충돌 사본 "제목 (충돌 사본, 기기 이름, 날짜)" 으로 만든다. 사본 uid 는 H(원본 uid, 진 쪽 칸 시각, 진 쪽 본문 지문)라 어느 기기가 만들어도 하나로 합쳐진다. 메모 목록에 "충돌 사본" 표시가 붙는다. (3판) 세 갈래 합치기에는 base 의 글이 필요해서 `sync_seen` 에 지문과 함께 본문도 둔다(메모 크기의 사본 하나). 보내는 덩어리에는 지문만 싣는다. 받은 쪽이 "보낸 기기가 고쳤나"를 `본문 지문 != 보낸 base 지문` 으로 보고, "이 기기가 고쳤나"를 `본문 지문 != 마지막으로 맞춘 지문` 으로 본다. 둘 다 고쳤고 두 base 가 같으며 진 쪽이 base 끝에 덧붙인 것이면 합친다(이긴 쪽 글 뒤에 덧붙인 부분을 잇고 칸 시각은 둘 중 큰 값 + 1: 같은 시각의 이긴 쪽 본문에 다시 지지 않게). 합치지 못하면 사본이다. 처음 보는 항목은 base 를 모르므로 둘 다 고친 것으로 본다. 사본 제목의 날짜는 진 쪽 칸 시각의 UTC 날짜(기기마다 같게), 사본의 모든 칸 시각은 진 쪽 본문 시각이다. 사본 표시는 `sync_copy`(사본 uid, 원본 uid)에 둔다.
- **지우기:** 휴지통으로 보낸 것(`deleted_at`)은 칸 하나처럼 맞춘다. 한쪽이 지우고 다른 쪽이 고쳤으면 나중 것이 이긴다. 영구 삭제는 삭제 표식으로 맞추며 되살리지 않는다(한 기기에서 영구 삭제하면 모든 기기에서 사라진다. 휴지통 30일이 그 전 마지막 기회다). 삭제 표식보다 나중에 같은 uid 로 다시 만든 항목은 산다(같은 uid 행이 다시 들어오면 앱이 표식을 지우고, 엔진은 받은 표식의 t 와 그 행의 만든 시각을 비교한다). (3판) 만든 시각은 그 행의 `created_at` 칸 시각이다(행을 넣을 때 트리거가 적는다). 표식 덩어리는 `{kind, uid, tomb: t}` 를 잠근 것이고 서버에는 `deleted: true` 로 올린다(서버가 90일 뒤 덩어리를 비우면 종류를 모르니 모든 표에서 그 uid 를 지운다). 보낸 뒤에는 표식을 정리한다. 할 일을 영구 삭제하면 단계마다 삭제 표식을 남겨 서버에서도 지운다.
- **반복 할 일:** 다음 회차 uid 는 H(이전 회차 uid, "next") 다. 마감 날짜는 넣지 않는다(끝낸 날에 따라 달라지므로). 다음 회차를 만들 때 같은 uid 행이 이미 있으면(지워졌거나 되돌리기로 걷어 낸 것이어도) 새로 넣지 않고 되살린다. 지금 코드는 끝냄, 되돌림, 다시 끝냄에서 다음 회차가 둘 생기는데 이것도 같이 고친다. 회차마다 복사되는 단계 uid 는 H(새 회차 uid, 원본 단계 uid).
- **반복 일정:** (3판) 지웠다 되살려 원래 상태(손대지 않은 펼친 회차)로 돌아온 회차는 추적 대상이 아니지만, 서버가 아는 것이거나 칸 시각이 남은 것이면 보낸다. 안 그러면 되살린 것이 다른 기기의 지움을 이기지 못한다. 앱은 반복 회차를 최소 1년 앞까지 행으로 미리 만든다(`event-store.ts:583`, 최대 730일). 매일 반복 하나가 1년에 365개라 회차를 모두 보내면 금방 상한에 닿는다.
  - 펼친 회차는 `slot`(만들 때의 원래 시작 시각, 옮겨도 안 바뀜) 칸을 갖고, uid 는 H(시리즈 uid, slot) 다.
  - 보내는 것: 시리즈 묶음(첫 회차 행, `event_repeat_template`, `event_repeat_skip`), 고친 회차(`user_edited`), 휴지통으로 보내거나 되살린 회차. 손대지 않은 회차는 각 기기가 시리즈에서 다시 만든다.
  - 적용 순서: 시리즈 묶음, 건너뛴 회차, 고친 회차. 고친 회차를 적용할 때 같은 slot 의 펼친 행이 있으면 그 행을 갈아끼운다(같은 uid 라 겹치지 않는다). (3판) uid 가 다른 손대지 않은 펼친 행이 같은 시리즈 같은 시각에 있으면(uid 정리가 못 한 행) 그 행을 지우고 받은 행을 넣는다.
- **코인:** 할 일에 `coin_paid`(어느 기기에서든 이 할 일로 코인을 받음) 칸을 두고 맞춘다. 참이면 다른 기기에서 다시 끝내도 코인을 주지 않는다. 되돌리기 환불은 코인을 받은 기기에서만 한다. 되돌리기로 환불하면 `coin_paid` 를 0 으로 되돌린다(그 기기가 환불했으니 다시 끝내면 받아야 한다). 24판이 기존 행을 채울 때도 장부의 순 지급(todo, early, undo 합)이 0 보다 클 때만 1 로 둔다. 받은 할 일의 로컬 번호는 지금 규칙(가장 큰 번호와 코인 장부 번호 다음, `todo-store.ts` 의 `NEXT_TODO_ID`)으로 정해 코인 지문이 겹치지 않게 한다. 받은 완료는 `coins` 칸 0 이고, 끝내기(`complete`)는 `coin_paid` 가 1 이면 코인을 주지 않는다. 두 기기가 오프라인에서 같은 할 일을 동시에 끝내면 한 번 더 받을 수 있는데, 남는 위험으로 둔다.
- **알림:** 받은 알림은 이미 지난 것을 울리지 않는다(`notified_at` 을 지금으로 두고 넣는다). 같은 알림이 두 기기에서 울릴 수는 있다. (3판) 마감이나 시작이 옮겨졌으면 이미 말한 표시를 지우고 다시 센다. 그대로면 이 기기의 표시를 둔다.
- **구글 캘린더:** 구글 보내기 기록(`google_*`)은 맞추지 않는다. 대신 구글 일정 id 를 항목 uid 에서 정해(구글 id 규칙 a~v, 0~9, 5~1024자에 맞게 uid 를 base32hex 로) 어느 기기가 보내도 같은 id 가 된다. 두 번째로 보낸 기기는 409 를 받아 고치기로 바꾼다. 다른 구글 계정을 연결한 기기에서 404 가 나도 그 기기 기록만 지운다. 두 기기 시험을 가장 두껍게 한다. (3판) 새 일정만 `jjk` + base32hex 26글자(uid 의 128비트)로 정하고, 이미 구글 id 가 있는 일정은 그대로 둔다. uid 가 없는 24판 앞 행은 예전처럼 무작위다. 정한 id 로 넣었다가 409 뒤 고치기도 404 이면(구글에서 지운 일정의 id) 같은 id 로 맴돌지 않도록 무작위 새 id 로 바꿔 넣는다.

### 처음 켤 때와 되살릴 때
- 첫 기기: 가진 항목을 모두 올린다.
- 다음 기기: 서버 항목을 받고, 자기 항목도 올린다(합집합). 두 기기가 같은 백업 파일에서 되살린 경우는 uid 가 같아 하나로 합쳐진다.
- 백업 되살리기: 되살리기 전에 "동기화가 켜져 있어. 되살린 내용이 다른 컴퓨터에도 맞춰져" 를 묻는다. 되살린 뒤에는 기기 번호를 새로 만들고 전부 다시 받는다. (3판) 되살린 항목도 모두 보낼 목록에 넣어 합집합으로 맞춘다. 칸 시각은 백업 때 것이라 그 뒤 다른 기기에서 고친 칸은 새 쪽이 이기고, 그 뒤 영구 삭제된 항목은 되살린 행의 만든 시각이 표식보다 앞서면 다시 지워진다. 되살린 내용이 다른 컴퓨터의 새 편집을 덮지는 않는다.

## 10. 남는 위험
- 복구 코드를 잃고 기기도 모두 잃으면 서버 사본은 끝이다. 화면과 처리방침에 분명히 적는다.
- 한 기기에서 영구 삭제하면 모든 기기에서 사라진다. 휴지통 30일이 마지막 기회다.
- 두 기기가 오프라인에서 같은 할 일을 동시에 끝내면 코인을 한 번 더 받을 수 있다.
- 같은 알림이 두 기기에서 울릴 수 있다.
- 반복 일정과 구글 보내기는 지금도 복잡한 곳이라(21판에서 중복 정리 이력) 두 기기 시험을 가장 두껍게 한다.
- 시계가 크게 틀린 기기는 하루 앞까지는 칸 시각을 앞세울 수 있다(6절에서 하루로 자른다).
- (3판) 시계가 하루 넘게 앞선 기기는 자기 칸 시각이 계속 이긴다. 받는 쪽이 하루로 자르는 것은 다른 기기의 시계를 끌고 가지 않게 할 뿐이다. 그 기기의 시계를 맞춰야 한다.
- (3판) 반복 일정 시리즈 원본을 영구 삭제한 뒤 남은 회차는 다른 기기에서 시리즈 연결 없는 일정이 된다(연결을 보낼 uid 가 없다).
- 24판 저장 파일은 23판 앱이 열지 못한다(지금 규칙대로 메모리로 열고 알린다). 올리기 전 자동 복사본(`jjakkung.db.bak-v23`)이 남는다.
